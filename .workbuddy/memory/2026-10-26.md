### 为什么连 REWRITE-PLAN 一起删

用户只说删交接文档，但"重写方案"同样是过程文档：§3 的模块设计稿与代码
注释重复（1121 行里约 700 行），§4 是阶段进度表（阶段已不存在），§6.2.5
还留着"自投仍未实现"这种已经过时的说法。留着它的代价是"当前状态"永远
有两个版本，而且每加一个功能要同步三处。

真正要留的是**决策与理由**，所以新写了 `docs/DESIGN.md`：
定位、分层（含 R1-R6 六条硬约束）、七个关键决策（服务端纯转发 / id 是稳定
身份 / 一条连接承载全部操作 / 分块与背压 / 续传与残片校验 / 文件子系统 /
Qt 前端边界）、**已否决方案 + 改口条件**（P2P、双连接、BaseAskDF、4 MiB 块）、
工程标准、决策记录表。

"已否决方案 + 改口条件"这一节是原文档里最有价值、最容易在重写中丢失的部分：
它记录的是"为什么不能这么做"，只有结论没有理由时，下一个人会重新踩一遍。

## 顺带发现：README 有两句假话

清理时核对实现，发现 README 写着：

1. "服务端只做信令与中继，**能直连就直连**" —— P2P 没实装（550/551 是占位）
2. "中继时**端到端加密**" —— 只有 `kFlagEncrypted` 标志位和 §6 的载荷布局，
   **发送路径根本不加密**（`grep kFlagEncrypted` 在实现里只有定义、没有使用）

`PROTOCOL.md` §6 也照原样描述加密布局，读者会以为线上是密文。已修：

- README 表格改成如实描述（中继只转发不落盘、完整性靠两端 Merkle 校验），
  并加一条明确提示"载荷目前不加密，需要保密请套隧道"
- PROTOCOL §6 开头加"状态：布局已定，尚未实装"，并指出实装前要先做密钥协商
  （nonce 唯一性靠会话密钥保证）

**教训**：文档写着"设计"很容易被读成"实现"。凡是只有布局/标志位没有调用点的
东西，必须在文档里显式标状态——这条之前只在 HANDOFF 里靠记忆维持，现在写进
了正文。
