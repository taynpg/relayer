# 2026-11-04

## 吞吐：从 25-48 MB/s 到 200-300 MB/s

用户指出 v1 轻松 260 MB/s。上一轮我只定位到"引擎是定时器节拍驱动"，
但按那个结论去改（事件驱动 ACK、事件驱动发送、调 tick、调窗口、调线程池）
**全都没效果**——因为真正的原因有六个，每一个都能单独把吞吐钉死。

### 六个原因（按实测收益排序）

1. **`FrameReader` 逐字节操作 `deque<char>`**
   ```cpp
   for (i < frameLen) contiguous.push_back(*it++);   // 26 万次迭代器
   for (i < consumed) buffer_.pop_front();           // 26 万次 pop
   ```
   单帧 4-5ms。**这是"块越大越慢"的来源**——之前测块大小怎么调都是 40 MB/s
   就是这个。改成 `vector<char>` + `readPos_`：整帧一次 memcpy，消费一次
   指针加法，压缩摊销 O(1)（读指针过半才搬一次）。

2. **每块算两次 SHA-256，其中一次纯浪费**
   `computeDigestSync` 既 `sha.update()`（整文件摘要）又让 `MerkleBuilder`
   算叶子哈希。而 `desc.sha256Hex` **只被编码进请求帧，接收端从不读取**
   （协议本来就允许空）。去掉后 256MB 少 837ms。

3. **发送前建根单线程** → 分段并行（8 线程，连续区间保证顺序读）
   837ms → 194ms。

4. **接收端收尾重读整个残片建根** → 写盘时顺手算叶子哈希
   原注释说"写盘是乱序的，攒叶子等于再留一份完整文件"——**这个推理错了**：
   存的是每块 32 字节的摘要，1GB/256KB 只有 128KB。
   **续传时有坑**：残片里已有的块不走写盘路径，叶子哈希是空的 → 根算错
   → 校验失败、残片被删。用 `leafReady_` 标记 + 回退重读。

5. **Windows 默认定时器分辨率 15.6ms**
   `tickInterval = 10ms` 实际 15.6ms，改 2ms **还是** 15.6ms。
   线索：ACK 间隔恒定 15.6ms，与任何配置无关。
   修：`common/TimerResolution.h`（RAII 的 `timeBeginPeriod(1)`），
   cli / server / app 三个入口各装一个。

6. **背压时丢块且不回 ACK**
   `acceptChunk` 返回 kBusy 后直接 `return`，对端只能等重传超时，期间窗口
   一直被占。改成立刻回一次 ACK（基于 `written_`，不会谎称收到），对端
   据此马上补发。1GB 重传 20 → 0。

### 参数收敛（都有实测依据）

| 参数 | 新值 | 依据 |
|---|---|---|
| `windowBytes` | 12MB（48 块） | **必须明显小于** `maxBufferedChunks`(64)；两边相等时 1GB 有 21 次重传、掉到 212 |
| `maxReadInFlight` | 16 | 与窗口匹配，两三批填满一窗 |
| `maxBufferedChunks` | 64 | 16MB 缓冲，是背压着力点 |
| `maxWriteInFlight` | 16 | 写盘在 writeMu_ 上串行，这只影响排队深度 |
| `tickInterval` | 2ms | 10ms 时 1GB 只有 188 + 20 次重传（批量太大顶满缓冲） |

### 实测（Release，回环，经中继）

    64MB 199 / 256MB 235-257 / 512MB 255 / 1GB 280-298 MB/s，全部零重传

### 方法论（比结论更值钱）

**先量各阶段耗时，不要按参数直觉调。** 这次埋了 `RELAYER_PROF=1` 的分段
计时，才看到"单块各阶段合计 0.5ms，而端到端 5-8ms"——90% 在等，而等的
原因分散在六处。

**改参数完全无效时，先怀疑参数没生效**（定时器分辨率就是这个）。

**"调了没效果"本身就是信息**：说明瓶颈不在那一层。我上一轮把窗口、ACK、
线程池全试了一遍都没用，正确的结论应该是"那几层都不是"，而不是"再多试几组"。

### 环境坑

Git Bash 里链接失败时 collect2 的 stderr 会被吞掉，只剩
`collect2.exe: error: ld returned 1/5 exit status`。同样的命令换原生 shell
能看到 `undefined reference to ...`。这次为此浪费了不少时间（一度怀疑内存、
磁盘、工具链损坏）。

# 断线重连（README 路线第三项）

## 做了什么

`cli::Client` 的 `ClientConfig::ReconnectPolicy`：

```cpp
struct ReconnectPolicy { bool enabled; ms delay{2000}; ms maxDelay{30000}; int maxAttempts{0}; };
config.onReconnecting = [](int attempt, ms delay);
config.onReconnected  = []();
```

CLI 开关：`--reconnect` / `--reconnect-delay` / `--reconnect-attempts`。
契约行 `RECONNECTING attempt=N delay_ms=M` 与 `RECONNECTED`（e2e 断言用）。

两条链路分别处置：只有数据连接断了就**立刻重建那一条**（不消耗重试次数，
控制连接陪着再握手纯属浪费）；控制连接也断了才走指数退避。

## 三个必须记住的设计点

1. **发送作业要跨重连存活**。`sends` 从 "TransferLink 的 job id → entry"
   改成 "本进程稳定编号 → SendJob{linkJobId, source, remoteName, peerId}"，
   外加 `linkToSend` 反查表。重连后 `resumeSends()` 按 linkJobId==0 的挑出来
   重新协商 + 重发；对端 `.relaypart` 续传会跳过已落盘的块。
2. **打断 ≠ 失败**。链路断开时 TransferPeer 给的是 `kLocalCancelled`，与用户
   取消分不开。判据落在 `Session::finished() || !linkAlive()`（新增
   `Connection::isActive` → `Session::linkAlive`）。为什么不能只看 finished：
   对端关了 socket 之后、本端读到 EOF 之前，send 会以 "connection is not open"
   失败，某一路 job 正是这么结束的。
3. **断线时挂起的控制请求不能当场 finish**。ControlLink 先 failAll 再回调
   onClosed，请求失败的那一刻还不知道该不该重连。统一走 `failRequest()`
   把结论 post 一拍，onClosed 之后再判。

## 顺带挖出来的残片 bug（比重连本身更值钱）

现象：断线重连后续传，最终 merkle 根对不上，残片整块作废。

根因：**写盘是乱序的**（每块 seek 到自己的偏移），文件长度会越过真正的
连续区；而续传点只能从**长度**推（新进程没有位图）。中间那些洞被当成
"已有数据"跳过。

修法：`abort(keepPartial=true)` 时截到 `contiguousWrittenBytes()`；
并且 `TransferPeer::finish()` 在非 kCompleted 退出时也 abort(true)——
之前只有 cancel() 会 abort，"自己先撞上写失败"那条路径直接 finish 就走了，
残片留着带洞。

**排查方法**（值得复用）：断线瞬间把 `.relaypart` 与源文件**逐字节**比，
打印首个差异偏移与差异字节数。只比大小、或者只看"最后传完了没有"，
都发现不了这个 bug。首轮 6 次里错 1 次，属于"必须多次跑才看得见"的类型。

## 踩到的坑

- **`_chsize_s` 会补零扩展**：keepBytes 算大了不是"没截断"，而是把文件
  变长并填零——症状更怪（前缀正确、中间一片零）。
- **`scheduleReconnect` 的防重入标记会把自己挡回去**：连接看门狗超时那条
  路径调它时 `reconnectPending` 还是 true，于是既不重试也不报错，进程静默
  挂死（e2e 表现为 300s 超时）。修法：进 `scheduleReconnect` 之前先清。
- **重连成功后必须 cancel connectTimer**：它是每次尝试重新上弦的，不撤的话
  15 秒后会以"这次重连没成功"再排一次重连。
- **协商预算要分场景**：普通场景 40×200ms=8s 够；重连后对端也在重连，
  8s 偏紧 → 150 次（30s）。
- **`build/` 是 Debug、`build-rel/` 是 Release**，e2e 默认用 `build/bin`。
  只编 Release 就去跑 e2e，会看到"未知选项 --reconnect"这种莫名其妙的错误。
- 用 python 改仓库文件会写出 CRLF，之后必须显式转回 LF（`.gitattributes`
  是 eol=lf）。

# 载荷加密（README 路线"附加"之一）

## 形状

`cli::Client` 的 `ClientConfig::encryptPassphrase` → 在 Impl 构造时派生**一次**
（PBKDF2 两万次迭代）→ 同一个 `shared_ptr<const PayloadCipher>` 交给
ControlLink 与 TransferLink 的 Config → 各自塞进 `SessionConfig::payloadCipher`。
CLI 开关 `--encrypt <口令>`。

Session 的接缝只有两处：
- `send()` 末尾：`cipher && role==kClient && !to.empty() && !isEncrypted()` → 加密
- `handleInbound()` 尾段（交给上层之前）：`isEncrypted() && role==kClient` → 解密

**中继既不解密也不拒绝**：它没有口令，拒绝就等于"中继不让你用加密"。
判据是 `to` 是否为空（发给中继的帧它要读懂），不是帧类型白名单——白名单
将来加新帧会静默漏加密。

## 三个必须记住的坑

1. **AAD 里的 flags 必须规范化**（置加密位、清 CRC 位）。CRC 位是打包时按
   body 长度定的，加密发生在打包**之前**——发送方算 AAD 时不知道最终长度，
   接收方拿到的帧里却已经定了。不抹掉这一位，**所有帧都解不开**，而且症状
   是"口令明明一样却解密失败"。
2. **nonce 必须每帧随机**，不能用计数器：密钥是长期口令派生的，进程重启、
   多条连接都会从 0 重来，计数器方案必然撞车。GCM 撞 nonce = 明文异或泄露，
   外部完全看不出来。
3. `PayloadCipher` 头文件里我第一版**忘了写 `namespace relayer::protocol {`**
   （只写了结尾的 `}`），报的是一堆 "'crypto' has not been declared" —— 看着
   像 include 路径错了，实际是命名空间没开。看到"整片类型都不认识"先看
   命名空间配对。

## 口径要一致

- 口令 ≠ 认证口令：中继知道认证口令，用它派生密钥等于没加密。文档里
  反复强调这一点（README / PROTOCOL §6 / DESIGN §3.1.1）。
- 默认关：它要求两端事先约定口令，而"打开就能用"是这工具的前提。
- 不静默降级：解不开就断开。最坏的失败方式是"用户以为加密了"。
- 已知代价：发送方要等请求超时（约 10 秒）才知道对端不接受；加"我解不开"
  应答帧会打破"加密对中继透明"，暂不做。**kAuthFailed 排除出重连**，
  否则口令错会变成无限重连。

## 验证

单测 9 个（往返 / 空 body / nonce 不重复 / 错密钥 / 篡改密文 / 篡改 AAD 的
type / AAD 规范形式 / 打包解包往返 / 同口令派生一致）；e2e 两个场景；
手工验过加密下的自投（服务端绕回本连接）与远端列举（控制连接上的对端帧）。
Release 下 64MB 加密 906ms vs 明文 1208ms——开销在噪声内。
Debug 下曾看到 26MB/s，那是 Debug 版 AES 慢，别当性能问题。

# 块载荷压缩（README 路线"附加"的最后一项）

## 形状

`--compress` → `ClientConfig.compress` → `TransferLink::Config::compress`
→ `TransferPeer::Config::sender.compress` → 在读盘任务里 deflate。
接收侧**不需要配置**：按帧上的 `kFlagCompressed` 逐帧处理。

- 压缩点：`TransferSender` 的读盘 lambda（WorkerPool 线程），压不动就按原样发；
- 解压点：`TransferReceiver` 的写盘 lambda，容量 = `lengthOf(idx)`（兼长度校验
  与压缩炸弹边界）；
- 叶子哈希与 Merkle 根始终算**原文**，残片里存的也一直是原文。

## 关键判断：为什么不在 Session 层做

Session 层（像加密那样）最省事，但压缩**必须在工作线程上**：deflate 一块
256 KiB 是毫秒级 CPU，压在 io 线程上会让心跳、ACK、写队列一起排队。加密没
这个问题是因为 AES-GCM 快一个数量级，而且它的调用点本来就在 io 线程上
（额外开销 <0.1ms）。

## 顺带修掉一个真 bug：背压上限是"两个名字一个计数器"

现象：压缩后的 28MB 文本传输要 3.2 秒（比不压缩 276ms 慢十倍），
`chunksRetransmitted=6`，接收端 `背压丢块=6`。

根因：接收端有两个上限，`maxBufferedChunks=64` 与 `maxWriteInFlight=16`，
它们**卡的是同一个计数器**（已收未落盘块数），等于取小值 16——而发送端窗口
是 48 块。于是"窗口一贴边就丢块"是必然的，丢了只能等满 3 秒重传超时
（`checkRetransmit` 是唯一的重发触发点；注释里写的"对端收到 ACK 就会立刻
补发"其实没实现）。

修法：删掉 `maxWriteInFlight`。写盘在 `writeMu_` 上串行，"并发写盘数"只是
线程池队列深度，不是独立约束。删完同一场景 3.2s → 0.23s，零重传。

**教训：两个名字不同的上限，如果卡的是同一个计数器，小的那个才是真实配置，
而文档写的是大的那个。** 平时是隐性浪费，换一种流量形状（压缩、大块、快
链路）就变成显性故障。

## 验证

- 单测：Deflate 5 个（往返、压不动返回空、空输入、按期望长度封顶、损坏/截断），
  接收器 2 个（压缩块解压后内容正确且能混着发；解压失败必须变成写失败、
  该块不进 written_）。
- e2e：`compressed-transfer`（断言 `payloadBytesSent < 1/4 文件大小` ——
  内容对不对**证明不了**压缩生效，根是按原文算的）、`compressed-incompressible`
  （`payloadBytesSent == 文件大小`）。
- 实测：28.4MB 文本 → 107KB 上线，228ms；16MB 随机数据 → 原样 16MB，零重传。
