## 后续：E4 的 e2e 半边——补 no-auth 场景（590200e）

### 场景设计（tests/e2e/run_e2e.py）

`Cluster.start_server(no_auth=)` / `cli_common(no_auth=)` / `start_receiver(no_auth=)` /
`send(no_auth=)`，默认值保持原行为，其余场景零改动。三条断言：

1. 两端 `--no-auth` → 2MB 传输成功、哈希一致、无残片（证明无认证是真正的
   握手路径，不是"跳过握手"）。
2. 带 `--password` 的客户端连无认证中继 → 非零退出。断言退出码不断言文案。
3. 口令与 `--no-auth` **都不给** → 非零退出。

顺序有讲究：负例必须在 recv 还活着时做，否则失败原因是 answerTimeout，
测不到认证层。

### 当场抓到的真缺陷（已修）

`cli/src/main.cpp` 的注释写着「认证方式必须恰好声明一种」，代码只实现了
「不能同时给」。什么都不给时客户端拿空口令按认证模式去连，用户只能从
协议层 `unauthenticated peer sent non-auth frame` 反推自己漏了参数。
补上缺失分支后，报错变成"必须提供 --password，或用 --no-auth 声明中继已
关闭认证"。

- `parseArgs` 在匿名命名空间里，**单测够不着**，所以这个缺口一直没被发现；
  e2e 是唯一能看门的地方。
- 口令客户端撞无认证中继 → 服务端跳过握手直接发 answer_id → 客户端按相位
  错误拒绝 + 追加"请加 --no-auth"提示。这是 `Client.cpp` 里**有意设计**的
  路径（onClosed 分支），不是 bug，别去"修"它。

### 顺带修的既有 flaky

`ConnectionTest.cpp:542` "resolving a bogus host reports failure" 的 5 秒上限
在本机 resolver 上不够：Release 全量跑两败两过，失败时 core_test 从 9s 拖到
18s（说明是真的卡在 DNS，不是代码不回调）。改成 30 秒——它本来就是上限，

**教训**：`ctest` 全量里偶发红的用例，先单跑确认是否偶发、再循环跑抓现场，
不要因为它"重跑就过"而放过——flaky 测试会训练人忽略红灯。

### 连接按钮（用户报的问题：连上后【连接】还能点）

根因不只是少个状态判断，而是【断开】根本没断开：

- `ConnectorControl::onClearClicked` 只清表格，会话还活着；而【断开】按钮按
  `busy` 禁用，连上后 busy 恒为 true → **永远点不动**。于是用户唯一能点的就是
  【连接】，每点一次顶掉常驻会话、白耗一个 id。这正是文档里"点一次刷新 id 涨
  一号"那类回归的入口。
- 改法：`connected_` 只在拿到**非空** id 时置位；【连接】= `!connected_ && !busy`；
  【断开】只看 `connected_`；【断开】经 `disconnectRequested` 交给 MainWindow，
  由它**先清 `receiveWanted_` 再 cancelCurrent**——否则 abort 引发的
  `operationFinished` 会走"接收会话失败自动重连"路径，表现为"断开后自己又连上"。
- 换中继地址的路径因此固定为 断开 → 连接（tooltip 里写了）。

`build/bin` 里 4 个用户进程占着 exe，`ld returned 1 exit status` 且无诊断。

## 固定标识（kClaimId）实现（2026-10-23 下午）

用户需求：v1 那种"自己设标识、撞名拒绝连接"的语义。理由是对照表按 id 固定
投递，id 漂移会发错人（真实事故）。设计先入档（`REWRITE-PLAN.md` §6.2），
随后按协议先行实现。

### 落地

- 协议：新帧 `kClaimId=134`（body `u8 len || id`），应答复用 `kAnswerId`，
  status 加 2=占用 / 3=非法；`ErrorCode` 加 `kIdTaken` / `kIdInvalid`。
- core：`PeerTable` 的 claim 编解码 + `IdAnswerStatus`；`Session::claimPeerId`
  （客户端声明）/ `assignPeerId`（服务端改名并通知）。
- server：`handleClaimId` 校验 → 占用检查 → 迁表（先摘旧号，让 registerPeer
  登记新号，登记逻辑只有一处）→ 改名；`idConflicts` 计数；`renaming_` 防
  重复计 authenticated。
- cli：`--id` 从"断言"改为"声明"；拒绝时给可照做的结论。
- app：连接面板「本机标识」输入框 + QSettings 持久化。
- 测试：`PeerTableTest` 6 组编解码；e2e `fixed-id`（4 条断言）。

### 实现中撞到的两个坑（都写进了 §6.2.5）

1. **先发应答再 close = 理由被吃掉**。`Connection::doClose` 清空写队列，
   拒绝帧发不出去，客户端只看到"连接断了"。改成只回 status，由客户端自己关。
2. **临时号应答晚于声明到达**。认证时服务端先发 `client-N`，那条 status=0
   的应答把 `claimPending_` 清掉，随后真正的拒绝被当成"无关应答"忽略——
   症状是撞名的客户端挂着不退出（e2e 60s 超时才暴露）。
   修法：`Session` 记 `claimTarget_`，只有拿到声明的那个名字才算结束。
   这个 bug 只有真进程能发现，单测覆盖不到（时序取决于两条应答的相对到达）。

另外：客户端在声明完成前**不对外宣布身份**（否则 `ASSIGNED_ID=` 会先打
临时号，污染 e2e 的 `head -1` 契约）。

### 验证

Debug / Release(-Werror) ctest 各 7/7；完整 e2e 14/14（Release 193s，1GB 128s）。

## 修正：远端浏览改为本地/远端两栏常驻（用户反馈"点了没反应"）

用户反馈点「浏览此对端的目录」后只有一行日志、界面像没反应。根因有两层：

1. **远端面板当时是"切换"而不是常驻**——切过去后整个面板重画，用户看不出
   变化（尤其远端没开共享时就是空表）。
2. **对端离线时服务端静默丢帧**（§11.3 没有"投递失败"），浏览请求永远没有
   回音 → 面板停在"读取中"。这条在 CLI 与 GUI 两条路径上都补了 10 秒
   应答超时（`browseTimer`），失败文案"对端没有响应（可能已离线）"。

按用户要求改成 v1 形状：下半部左右两个 `ExplorerControl` 并排
（"本地" / "远端（对端共享目录）"），远端没选对端时显示"<未选择对端>"
而不是隐藏。同一个类、两套数据源，仍符合上一轮纠正的方向。

教训：**异步 UI 操作必须有可见状态与超时**。只写日志、界面不动的反馈等于
没反馈；而"等一个永远不来的应答"在没有超时的协议里就是永久挂起。

## 修「点浏览此对端的目录后控件没反应」

用户反馈：布局 OK，但右键「浏览此对端的目录」后远端面板毫无变化。

### 三层原因（前两层是显示，第三层是缺反馈）

1. **`cbPath` 是非可编辑 QComboBox，`setCurrentText` 静默空操作**。
   非 editable 的 QComboBox 只在**已有项**里查找，找不到就什么都不做——
   于是路径框永远停在旧值。这就是"控件没反应"最直观的那一半。
   修法：远端路径用 `showPath()`（clear + addItem + setCurrentIndex）。
2. **表格本来就是空的**。远端没开共享时列出来也是 0 行，与"没反应"同形。
3. **失败原因只写日志**。用户看面板，不会去翻日志。加了状态行
   `lblStatus`（读取中 / N 项（M 目录 K 文件）/ 失败原因红字），并把
   远端分组标题改成 `远端 —— <对端名>`，切换成功与否一眼可见。

### 顺带补的两件

- **`self-browse` 自检入口**：GUI 的远端浏览走 `Client::browseOnSession`
  （请求搭在 kReceive 会话上），CLI 的 `ls` 走 `browsePeer`（一次性连接）
  ——**两条路不是同一份代码**，只测 `ls` 覆盖不到 GUI 那条。加
  `recv --share <dir> --self-browse`：自投把请求与应答都绕回本连接，
  一个进程同时当"问的人"和"答的人"，把 browseOnSession + serveFileList
  在同一会话上并存也验了。e2e 场景 `self-browse`。
  **这是个可复用的手法**：GUI 独有的路径 → 在 CLI 上做一个自检开关，
  否则那条路永远没有自动化覆盖。
- **共享目录入口从日志右键移到「设定」对话框**（Setting.ui 的 gbShare）。
  日志右键是"接收目录"的地盘，而共享是"给别人看什么"，两个概念。
  同一设置两个入口 = 改了一处以为生效。保存后提示"下次连接生效"
  （会话启动时已拷走配置）。

### 验证

`relayer-cli recv --share <dir> --self-browse` 手工跑通（REMOTE_LIST status=0
count=2）；e2e 17/17（Release 210s）；Debug 与 Release(-Werror) ctest 各 7/7。

## 架构判断：不抽 BaseAskDF 式的文件访问抽象

用户问 `ExplorerControl` 能不能对文件访问抽成 v1 那种 `BaseAskDF`，而不是
到处 `if (source_ == Remote)`。**结论：不做**，理由写进了
`REWRITE-PLAN.md §7` 的决策记录（含改口条件）。

关键事实（查过才说的）：

- v1 的 `ExplorerControl.cpp` 里有 **11 处** `askType_ ==`。它抽象掉的是
  "文件操作"，方向语义（上传/下载、拖拽源与目标）仍靠类型判断。
  所以"消灭类型判断"是伪目标——用户记忆里的"v1 是统一的"只对一半。
- v1 的 `RemoteAskDF::Request` 用 `promise` + `future.get()` **阻塞**，
  配 `WorkerThread` + `WaitDialog` 把异步藏起来。v2 照抄等于倒退。
- v2 的 8 处里 5 处是**路径语义**（home/parent/join/display），该写成普通
  私有函数，不需要类层次；真正要抽象的 IO 分支只有 1 处。
- 没有第二个消费者，且阶段 F 剩余项（打包/P2P/多任务并行）都不引入第三
  种浏览源。

**教训**：被问"能不能"时，先数一遍对方当作参照的那个实现里有多少同类
分支——这次数出 11 处，直接推翻了"v1 做到了"这个前提。

## 顺手修的正确性问题：远端条目名单段校验

`joinRel(currentPath_, name)` 直接拼对端给的名字。正常文件系统不会给
`..`，但这依赖对端的善意。

- **解码层**（`FileList.cpp` 的 `decodeAnswerFileList`）：名字必须单段
  （非空、非 `.`/`..`、不含 `/`），违背则**整份应答判错**而不是跳过该条
  ——只丢一条会表现成"目录里莫名少了个文件"，更难查。
- **编码层**同样规则（`DirEntry.name` 不该含分隔符，出现即本地有 bug）。
- **反斜杠不拦**：Unix 允许文件名含它，那是合法文件；Windows 上它才是
  分隔符，那层判断放 GUI 双击处（`isPathLikeName`，用 `Q_OS_WIN` 区分）。
- 新增 4 条 `FileListTest` 用例（含"反斜杠必须被保留"这条反向断言，
  防止后人图省事把合法文件当攻击拦掉）。

`PROTOCOL.md §11.8` 补了这条硬约束与两条理由。

## 阶段 F2：远端取回（下载）

F1 之后紧接着做。动机：远端面板能看见文件却不能拿，是个说不通的半成品。

### 两个设计决策

**1. 不用已经存在的 `kFileRequestDown`(502) / `kFileAnswerDown`(503)。**

我一开始想直接复用这两个 v1 留下的占位帧（名字正合此题），查了才否掉：

- 拉模式下 A（请求方）不知道 `totalSize` / `chunkSize` / Merkle 根——它是
  接收方。这些只能由 B 在 `kFileRequestSend` 里给出，所以**无论如何都省不掉
  那一次 500**。
- `kFileAnswerDown` 的 body 与 `kFileAnswerSend` 同构（含 `resumeOffset`），
  两条应答都发的话 A 会收到两个续传偏移，还得再定一条"谁算数"的规则。

结论：502/503 信息量比 500 少，加了等于多一次往返换不到东西。**保持未使用**，
在 Frame.h 里标注"v1 遗留，不要拿来复用"，理由写进 PROTOCOL §11.9.2。

**2. 取回不另造传输，只解决"谁发起"。**

新帧 `kAskFilePull`(135) / `kAnswerFilePull`(136)。B 回完 status=0 之后，用
**普通的推流程**（`startSendOnSession`）把文件发给 A。A 侧零新逻辑：它的常驻
接收会话本来就在等 `kFileRequestSend`。

这样分块、Merkle、续传、限速全部沿用 §9，不用碰传输层。

**3. 共享即"可见且可取"**：`shareRoot` 一个开关同时管列举和取回，不另设
"只读/可下载"。只想让人看不想让人拿在点对点工具里不成立（对方截个图就绕过），
多一个开关只会多一处会设错的地方。

### 落地

| 位置 | 内容 |

| `PROTOCOL.md` §11.9 | 时序、为什么不用 502/503、status 表、边界（目录取回未做） |

`servePullRequest` 里"先回 status 再发文件"的顺序是必须的：反过来的话 A 会先
收到一个陌生的 `kFileRequestSend`，分不清这是自己要的还是别人塞的。写在注释里了。
