### 踩到的坑（重要，下次别重犯）

1. **liblzma 把第一次"零进展"吞成 `LZMA_OK`**（见 `liblzma/common/common.c`
   的 `allow_buf_error`）。解压侧要么在 `read()` 内部再转一圈，要么永远拿不到
   `LZMA_BUF_ERROR`——表现是"截断的归档被当成读完"。现在 `XzDecoder::read`
   的循环里显式处理了这个。
2. **`LZMA_RUN` 下的 `LZMA_BUF_ERROR` 不是错误**，编码器喂完一块就会遇到。
   一开始当截断处理，导致每次打包都失败。
3. **tar 的 chksum 字段是 "6 位八进制 + NUL + 空格"**，不是末位 NUL。
   写顺序反了会被自家读侧放行（校验时字段替换成空格），只有外部 tar 报错。
4. **tar 的填充要按"当前条目内的偏移"算**，不能按归档累计偏移。
   用累计偏移的话第二个条目起整体错位 512 字节，而第一个条目仍然正确。
5. **`TarReader::readData` 在流式场景下必须"有多少给多少"**，
   硬凑满 `outLen` 会让调用方以为卡住，而且已读字节的记账容易丢。
6. **ninja 增量构建有时不重编 `.obj`**，改了源码却看到旧行为时先 `rm` 掉目标文件。

### 设计决定

- **不单独立 `archive/` 目录**：它和文件子系统共用 `IFileStore`，分成两个库是多余的一层依赖
- **zip 暂不实现**：传输场景用不上随机访问；而且 zip 中央目录一坏整包报废，tar 能救回前面的条目

- **前导斜杠不拒绝而是收成相对路径**：这是 `IArchive.h` 第 3 条的既定语义

## 阶段 D 前半：core/transport（提交 30fe6c7）

### FrameReader（18 用例 / 678 断言）

零 I/O 的字节流切分器。**踩到一个真缺陷**：

`next()` 必须内循环。unpackFrame 丢掉前导垃圾时返回 kNeedMoreData 且
consumed 非零——帧就在后面，只是还没解析。直接返回 false 会让调用方以为
"还差字节"，而对端若已发完最后一帧，那帧就永远卡在缓冲里。
终止条件是 consumed == 0。

其它决定：deque 而非 vector（粘包要头部消费，vector::erase 是 O(n)）；
每次解帧拷到连续内存（unpackFrame 只要 (const char*, len)，别为它改成
迭代器接口）；缓冲有 2× 最大帧的硬上限（防恶意对端撑爆内存）。

### Connection（13 用例 / 152 断言，真实回环 socket）

- io_context 由调用方注入，本层零全局状态
- 每连接一个 strand，回调串行化，不用锁
- close() 只 shutdown+close+清队列，不等回调（在 strand 上等 strand 会死锁）
- **onClosed 投递前先把 std::function 拷出来**再 post：上层很可能在回调里
  丢掉最后一个 shared_ptr，lambda 还捕 this 就是 use-after-free
- **onClosed 只通知一次**：对端 RST 时读写各自报错，两条路径都走 doClose
- **发送按帧排队**，一次 async_write 只发队首一帧。并发 async_write 会让
  字节流交错——TCP 上最容易犯的错
- connect() 返回 shared_ptr，且允许 kConnecting 时 send() 入队

### asio 集成踩坑（重要）

1. **vendored asio 的 include 根目录是 `third_party/`，不是 `third_party/asio/`**。
   它内部用 `#include "asio/detail/config.hpp"` 互引，必须让 `<asio/...>`
   能解析。原来的配置下 `<asio.hpp>` 和 `<asio/io_context.hpp>` 都编不过。
   另外上游本来就没有 `asio.hpp` 这个总头文件。
2. **必须给 relayer_asio 标 `SYSTEM`**。asio 是 header-only，实现会在我们的
   编译单元展开，上游代码不满足 -Werror -Wsign-conversion / -Wold-style-cast，
   不标 SYSTEM 会有几十个来自三方代码的报错。
3. **asio 的 run_one() 在"没有就绪任务但有挂起异步操作"时会阻塞**，不是返回 0。
   测试里用 `run_for(时限)` 代替 run_one 循环，否则"连接还开着、断言已做完"
   的场景会永久挂死。
4. Windows 上连接被拒端口前会 SYN 重传，2 秒不够，测试给 8 秒。

## 心跳与超时（3.4.4，提交 8c09f86）

`core/transport/Heartbeat.{h,cpp}` + `tests/core/HeartbeatTest.cpp`（14 用例 / 766 断言）。

`HeartbeatPolicy::check(now)` 是纯函数：输入时间点，输出 `{kNone, kSendPing,
kTimedOut}`，不碰 socket、不碰定时器。抽出来的唯一理由是测试——超时逻辑
本质是对时间轴的判断，需要快进时间；散在定时器回调里就只能真的 sleep 20 秒，
那是 CI 偶发失败的头号来源。抽出来后十分钟的连接行为在微秒内跑完。

参数：空闲 20s 发 ping，10s 无应答判超时，1s 检查一次（最坏 30s 发现）。
几个刻意决定都写进了 `PROTOCOL.md` §8.5：

- 双向心跳，不用 TCP keepalive（keepalive 默认 2 小时才报死，且检测不到
  "对端进程卡死但 socket 还开着"）。
- 任何入站字节都算生命迹象，业务帧也算。心跳问的是"对端还有没有反应"，
  不是"对端是否遵循心跳协议"。
- 出站动作不重置空闲计时器——发 ping 不能当作连接健康的证据。
- 判定顺序：先看未应答 ping 是否超时，再看是否该发新 ping。写反会让死连接
  一直发新心跳（"空闲超 20 秒"在死连接上恒成立），问题被掩盖成"在重试"。
- 一个 ping 未应答时不重复发新的。
- 边界一律 `>=`，用 `>` 会出现"周期恰好等于阈值时永远不触发"。

## 会话策略（3.4.5，提交 78c2f03）

四个有名字的判定函数：`checkInbound()` / `identityToBind()` /

### 实现过程中修掉的两个真问题

1. **`planRoute` 的 `selfId` 一度误传成 `f.from`**。`from` 是对端**自称**的，
   拿它判断"是不是发给自己"，攻击者把 `from` 写成自己名字就能让本该转发的
   帧被本地受理。现在 `selfId` 只来自认证分配，有专门测试钉住。
2. **"该不该绑"与"绑成谁"必须分开**。合成一个函数后就测不了"未认证时有没有
   偷偷绑"。现在是 `identityToBind()` 判定 + `applyIdentityBinding()` 落笔。

### 补了 Connection::onEstablished

不是可选项。客户端不能靠"send 第一帧"启动会话——建连前 `send()` 只是入队，
而握手第一帧由**服务端**发起（§7.1），客户端手上根本没有帧可发。没有这条
回调，客户端只能在"我发了一帧"这个假事件上启动状态机，而那个假事件在网络
失败时永远不会到来。

`adopt` 里投递而非同步调用：同步会让调用方在自己的构造函数里被回调。

### 组装层独有的几个坑

- **回调必须 weak_ptr 绑 Session**：Session 持 conn_，conn_ 回调强引用
  Session 就成环，引用计数永不归零。
- **握手超时必须是独立于心跳超时的值**。卡在握手半路时对端可能活得好好的
  （正在算 20000 次 PBKDF2），心跳一直正常应答，永远不判失活。
- **心跳基线在 onEstablished 建立**，不在构造函数——构造到连上可能隔几秒。
- **finish() 投递而非同步通知**：它有很多调用点（含 Connection 帧回调）。
- **finish() 幂等且保留首个原因**：认证失败后底层连接紧接 EOF，被覆盖成
  "成功"会让上层不知道口令错了。

### 撞上的真冲突：forward() 与 send() 的身份规则互斥

`forward()` 先把 from 改写成发送者认证身份，而 `send()` 的出站断言只允许
"空或服务端自己的 id"——转发帧的 from 恰恰是别人的 id，于是**正确的转发
被自己的断言拒掉了**。

根因在文档：`PROTOCOL.md` §11.4 只写了"不许出现第三方身份"，漏了转发帧
这个正当例外。修法不是放宽断言（等于关掉兜底），而是承认出站帧有三类、
from 的合法集合各不相同且**互不相交**：

```
send()    → 空，或服务端自己的 id
forward() → 恰好是发送者的认证身份
```

现在 forward() 走自己的断言（bound == authenticatedId 且 to 非空），
send() 走 checkOutbound()，两者最终都调同一个私有 deliver() 落盘计数。
有一条测试用同一个 from="client-1" 分别调 send（拒）和 forward（收），
钉住两个入口不能合并。

**教训**：写"兜底断言"时要先想清楚它会不会把**正确的**路径也拦掉。
这次是文档先漏了分类，代码照着文档写，于是断言本身成了 bug。

### 挖出来的真 bug：accept() 预置了 assignedId_

原来 `Session::accept()` 里有一行 `session->assignedId_ = config.initialPeerId;`，
而 `enterAuthenticatedServer()` 用"`assignedId_` 为空"判断该不该调
`allocatePeerId`。两处叠加的效果是：**allocator 永远不会被调用**，配了等于没配。

修法：删掉预置，把"从哪取 id"集中到 `enterAuthenticatedServer()` 一处。
优先级经用户拍板定为 **allocatePeerId > initialPeerId > 空**（allocator 优先）。

### 排查这条 bug 花的时间比修它多得多

现象：测试里 `allocCalls == 0` 但 `assignedId()` 已经是 `initialPeerId`。
一路上做了这些（都白做了，但方法值得记住）：

1. 怀疑增量构建没重编 → `--clean-first` 全量重建，结果不变（排除了）。
2. 怀疑链接了旧库 → `ar x` 解包看目标文件、`objdump -d` 反汇编
   `enterAuthenticatedServer`，确认新逻辑（先查 allocator）确实在库里。
   这一步花了不少时间，但它是**唯一能证明"代码是新的、行为是旧的"的手段**。
3. 最后靠一行临时 `fprintf` 打出 `assignedId()` 的值，才看见它是
   `"should-be-ignored"`——问题不在编译，在我读代码时漏了 accept() 里那行预置。

**教训**：二进制里"代码是新的"和"行为是对的"是两件事。先打一行值出来，
比反汇编快一百倍。反汇编应当留到"值显示代码没生效"之后再用。

### 另一个坑：`setPeerIdAllocator()` 的时序根本靠不住

`accept()` 同步调 `Connection::adopt()`，而 `adopt()` 立刻 `asio::post` 了
`onEstablished`——id 分配就在那个回调里发生。所以"accept 返回后再设置
allocator"能不能赶上，完全取决于调用栈有没有中途让出过。这不是稳定语义。

处理：方法是**软弃用**——改成返回 `bool`，认证后调用返回 `false`，
文档里写清"正确用法是构造前塞进 `SessionConfig`"。加了测试
`late allocator install is rejected after auth` 钉住返回值。

### PeerTable 的三条取舍

- 重名**不顶掉**先到者：顶掉等于允许后来者踢人，"谁是真的"不该由一次
  id 冲突隐式决定。
- 注销**不做静默幂等**：调用方要知道这次是不是真删了，否则会广播重复的
  下线通知（客户端列表跟着闪）。
- 用 `std::map` 而非 `unordered_map`：迭代顺序稳定，UI 列表不会因重哈希乱跳。

`allocateId()` 递增跳号，不是 `size()+1`——后者在有客户端下线后会发出一个
仍在使用的 id。写测试时这里错了两次（对 hint 推进的理解不对）。

### 心跳定时器

固定 `kTickInterval` 轮询，而不是"按到期时间设长定时器"。后者要在每次收到
数据时重置，漏一处空闲判定就失效；轮询每秒空转一次，相对 20 秒阈值可忽略。

### 为什么先补线格式

`PROTOCOL.md` §8.3 只有语义描述（"按块算哈希、合并成 Merkle 树、SACK
重传缺失块"），**没有任何字节布局**。直接照它写编解码，两端只能靠临时

所以先补 §8.3.1（树构造）与 §9.4–§9.8（六种载荷），再照文档写代码。

### Merkle 树：一个真实的"看起来对"的错误

第一版 `MerkleBuilder` 边收边合并上提。测试结果：

| 叶子数 | 结果 |
|---|---|
| 1, 2, 3 | 对 |
| 4 | 错 |

改成"维护多层待配对节点"之后 3 对了、7 又错。根因是**"奇数上提"在多层
结构里没有唯一答案**——3 个叶子时落单的 c 该当右操作数，7 个叶子时两层
各有一个落单节点，拼接顺序根本不唯一。

最终退回"存叶子、`root()` 时调 `computeRoot`"。用一点内存换"只有一份
形状实现"。这个决定写进了 `.cpp` 注释。

**教训**：增量算法与批处理算法"看起来等价"时，先测 1..9 的每个数量。
2 和 3 通过不代表 4 通过，4 通过也不代表 7 通过。

另有一次 `root()` 扫描方向写反：从低往高扫会把落单节点当左操作数，
`[a,b,c]` 算成 `node(node(c, node(a,b)))` 而不是 `node(node(a,b), c)`。
层级越高覆盖数据越靠左，所以必须**从高往低**扫。

### 验证方式：Python 独立实现

用 `hashlib` 按文档文字另写一遍，算出 0..9 块的根，与 C++ 逐条比对。
10 个值已作为金标准向量写进测试。

**为什么要两份独立实现**：C++ 参考实现和被测实现由同一人写、可能共享
同一个理解偏差。Python 那份照着文档另起一遍，`hashlib` 又是外部依赖。
两份都对上才说明"文档 → 实现"没走偏。

### `ackThrough` 的语义

必须记牢：**最长连续前缀长度**，不是"最后收到的块号 + 1"。

收到 0,1,5 → `ackThrough = 2`，位图第 3 位置 1。写成 6 的话发送方会以为
2、3、4 都到了，**数据丢失且不报错**，只有最终哈希能发现。

### 编解码的防御点

四条必须拒绝的畸形输入，都写进了测试：

- 未知状态码（否则"以后加新状态，老客户端误判为通过"）

- 描述有多余尾随字节（字段错位的前兆）

## 3.5.2 地基：WorkerPool + SendWindow（提交 6785209）

异步流水线的两个可独立测试的地基已完成并推送。

### WorkerPool
- 有界队列，`submit()` 队列满返回 false（背压信号，不阻塞 strand）。
- 析构契约：**已在执行的任务等完，还没开始的丢弃**。等是为了避免
  use-after-free（析构返回后 mutex_/queue_ 就没了）；丢弃是因为取消场景下
  排队中的写盘任务本来就不该执行。
- 测试用「条件变量/原子标志轮询 + 硬超时」而非 sleep 猜时序。

### SendWindow
踩了三个真坑，都记下来：

1. **`inUse()` 把 kPending 算作占用窗口** → 窗口 >= 总块数时所有块都
   "已占用"，`freeSlots()` 恒 0，一块都取不出，传输从第一步就死锁且不报错。
   正解：只有 `kInflight` 和 `kNeedRetransmit` 占窗口。
2. **`freeSlots()` 用 `total_ - acked_` 做上界** → 块一旦在飞，既没被确认
   也不能再被取走，这个上界会算出空位。正解：上界用 `pending()`。
3. **扫新块时不该在第一个非 kPending 的块上停** → 乱序 ACK 会在 ackThrough
   之后留下已确认块，停住就漏发。

其余语义：重传优先于新块（防重传饥饿）；位图基准点是**本次 ACK 的
ackThrough** 而非更新后的值；`acked_` 每次重算而非 `+=`（重复 ACK 会让
done() 提前为真）。

- 这台机器上手动 `g++ ... xx.a -o x.exe` 链接会失败，`collect2.exe` 只输出
  "ld returned 5"、**没有任何诊断**。排查方式是加临时 CMake 可执行目标，

- 调试这类纯逻辑 bug，`fprintf` 打点在不手动链接的情况下也得走 CMake 目标；

## 3.5.2 发送侧引擎 TransferSender（提交 523cb05）

异步读盘流水线。`pump()` 在 strand 上调度，`WorkerPool` 里读盘，上层
`takeReadyChunks()` 取走编码发帧。不碰 socket、不碰帧。

### 设计要点
- 每块各自 `seek`：共用流位置会让并发任务踩乱偏移，读到别人的数据但长度
  正确，只有最终哈希能发现。
- 「读完」≠「腾出窗口」：块从 `reading_` 移到 `ready_` 仍是 in-flight。
- `maxReadInFlight` 与窗口分离：前者是磁盘排队深度，后者是网络在飞量。
- 提交被拒时**按顺序**归还 batch 的失败后缀。
- 摘要（Merkle 根 + SHA-256）单独异步，不进 `open()`。

### 踩到的两个并发 bug（真 bug）
1. **`reading_`/`ready_`/`readError_` 无锁** → 偶发堆损坏 `0xc0000374`。
   worker 与 strand 同时改 vector。修法：`mu_` 保护全部，`readError()`
   返回副本（原来返回引用，且 `noexcept` 与 `lock_guard` 冲突）。
2. **任务 lambda 捕获 `this`，对象先析构** → use-after-free。修法：
   `runningTasks_` 原子计数（任务体入口加、RAII 出口减），析构自旋等到 0。
   只等已开始的，排队中的由 `WorkerPool::stop()` 丢弃。

### 测试教训
`inlinePost` **不等于同步整条链路**：它只让回调在提交线程执行，读盘仍在
池里。最初断言「pump 完就有 3 块」全错。加了 `drainUntil(sender, want,
autoAck)` 辅助：轮询 pump + 收块，`autoAck` 在窗口小于总块数时必需，
否则窗口被 ready 块占满、永远发不出下一批（那不是引擎 bug，是「只读不确认」
本身不构成完整传输）。

### 既有问题（与本次无关，已确认）
`[integration]`（ConnectionTest 的 loopback 用例）**偶发超时挂住**。
在基线 6785209 的干净 worktree 上复现（第一次就 exit=124）。
transport/ 与 session/ 本轮一行未动。待单独排查：
怀疑是 `onClosed` 只调用一次的用例与 io_context 停止时机之间的竞态。

### 已解决：`[integration]` "偶发挂住"（提交 0198450）

**结论：不是死锁，也不是竞态。是测试太慢，被外部 timeout 误杀。**

量出来的事实：整批 `[integration]` 稳定耗时 38163ms / 38188ms / 38166ms。
三次测量差 25ms——稳定得不像 bug，这正是"不是并发问题"的第一个线索。
基线 6785209 干净 worktree 同样 exit=124，确认既有问题。

根因：每条用例用 `pump(ctx, N秒)` 硬等。`run_for` 的时长是**上限**，
跑满才返回。一条只需 2ms 的用例写 `pump(2s)` 就真跑 2s，20 条累积 38 秒。
外部 `timeout` 一旦小于它，进程被 SIGKILL，表现成"挂住"且无任何失败信息。

改法：`tests/support/IoPump.h` 加 `pumpUntil(pred, timeout)`，分段推进
（每段 1ms）条件满足即返回。43 处硬等改掉，只剩两类保留固定时长：
纯否定断言（无完成信号）、前置动作（等 Challenge 发出），后者压到 ≤100ms。

**额外收获：暴露了三个真实的等待条件错误**，以前被"跑满时长"掩盖——
那些用例不是"通过"，是"慢到碰巧通过"：
1. `SessionTest` allocator 两条：只等 `server->authenticated()`，却断言
   `client->assignedId()`。后者要等 kAnswerId 到达客户端，是另一条路径。
2. `ConnectionTest:540`：等 `accepted`（acceptor 侧），断言
   `establishedCount`（客户端侧）。实测 20 次里 1 次失败。

**教训（写给以后的自己）**：写 `pumpUntil` 前先问"我要断言的到底是哪个量"，
等那个量本身，别等一个"看起来差不多同时发生"的邻近信号。跨两端的等待
尤其容易错。

验证：`[integration]` 8.2s 稳定，25 次连跑 0 失败；非 integration 273
用例 / 4929 断言全过；全量 ctest 6/6，总耗时 15.7s（core 从 38s+ → 14.3s）。

## 3.5.2 接收侧引擎（提交 fae6520）

`TransferReceiver`：先落盘后 ACK + `.relaypart` 残片 + 断点续传。

核心区别（决定整体设计）：发送侧只读、幂等，可以随便重读；接收侧落盘
**不可逆**。由此三条：先落盘后 ACK（flush 的理由是语义不是安全）、
每块自己 open 写流、残片与成品分离。

协议上撞到的事实：**Merkle 根不在 §9.4 的 desc 里**，只有 sha256 与
fingerprint，根是 kFileRequestComplete 才传。所以 `finalize(rootHex)`
收参数。按直觉从 desc 取会发现"没这个字段"。

### 顺带修的三个既有缺陷（都是本轮才暴露）

1. **`IWriteStream` 缺 seek**。乱序落盘必须能定位，接口却没有。补
   seek/tell。StdFileStore 先 flush 再 seek（让同步失败在正确位置报错），
   MemFileStore 用 pos_。

2. **`MemWriteStream` 是"整份快照回写"**。构造拷一份 node.content，
   commit 整份写回。4 个并发写流各持一份，最后 commit 的把别人的全覆盖
   ——症状是"只留一块数据、长度却正确"。改成脏区间提交
   [dirtyBegin, dirtyEnd)，且保留 flushOnClose(false) 的崩溃丢缓冲语义。
   注意：**只应用脏区间**是并发正确性的关键，不是优化。

3. **finalize 里读流没关就改名**。Windows 上 MoveFileEx 对仍有句柄的
   源文件失败（ERROR_SHARING_VIOLATION）；POSIX 不挡 rename。所以只在
   Windows 出现，表现"校验全过、就是改不了名"。显式 in.reset()。

### 踩坑

- **MemFileStore 不是线程安全的**（头文件早写明了）。并发用例必须用
  StdFileStore + TempDir，否则测的是 MemFileStore 的缺陷。
- **inlinePost 不等于同步整条链路**。8 条用例一起红在
  `writtenChunks()==0`，与发送侧当初一模一样。接收侧更容易误判，因为
  断言直接问"文件里现在是什么"。
- 测试里 ACK 位图断言写反：`bitmapTest(bm, i)` 的位 i 对应
  **块 ackThrough+i**，块 3 没收到时位 0 应为 false。

测试 22 用例 / 197 断言；core 573 用例 / 5126 断言；ctest 6/6；
接收侧 30 次连跑 0 失败。

## TransferPeer：传输会话门面（a259c90）

把 sender / receiver 接到真实 Session 上，跑通"收帧 → 解码 → 分发 → 回帧"完整回路。
回环 socket 上端到端，34 用例 / 171 断言，15 次连跑 0 失败。

**踩过的坑（都是真缺陷，已修）**

1. `SendWindow::freeSlots` 漏算 `kNeedRetransmit` → 活锁。
   块丢包后变 kNeedRetransmit：占窗口但不在 pending 里，`available = pending() = 0`
   直接短路掉 `byWindow`。而 `outstanding()` 只报 kInflight，重传扫描也看不见。
   两头都以为没活干。表现：65 块卡在 61 块，`chunksSent` 精确等于总数、一次重传都不发生。
   **诊断经验**：`acked` 涨但 `ackThrough` 不涨 + `dup=0` + `outstanding()=0` 这组合，
   指向"块既不在飞也没确认"，去查状态机第三态。

2. 接收方判重按大小放宽 → 静默覆盖用户数据。改为一律拒绝。

3. `f.from = session_->assignedId()` 在服务端会话上是**对端**的 id，不是自己的。
   `checkOutbound` 正确地拒了。统一在 `sendFrame` 清空 from：空 from = "就是我发的"，
   这是唯一在两个角色下都成立的写法。

4. 写盘完成必须回投一次 ACK。`acceptChunk` 只是受理，块还在池队列；而
   `buildCurrentAck` 依据 `written_`。漏了就是 100% CPU 活锁。

5. 等应答 / 等收尾都没超时 → 永久挂起。新增 `answerTimeout`(30s)、
   落实 `finalizeTimeout`(60s)。**一块都没发时重传超时看不到这条传输**，
   所以必须独立超时。

**测试写法**：`Harness` 里 sender / receiver 各用独立 `WorkerPool`。共用一个池会
让两侧任务互相挤占（虽然这次根因不是它，但分开是对的）。

**未完**：3.5.3 的"中途 kill 发送端"还需要进程级操作；`TransferPeer` 尚未接到 app。

### 根因一：接收端在传输开始前自杀（产品缺陷）

`checkIdle()` 只给发送方的摘要阶段开了豁免（`action == kSend && !started()`），
接收方等第一个请求帧时没有。`TransferPeer.h` 里 `started()` 的契约本来就写了
"接收方：open 成功之后为真"，**实现漏了一半**。`--idle-timeout 8` 下接收端认证
完 8 秒就退出，而 Debug 构建里发送端算 200MB 摘要要更久 → 请求还没发出对端没了
→ 发送方看到 `peer did not answer`，看着像中继丢包。

修法：判据统一交给 `!peer->started()`，不按角色分别判。idleTimeout 语义收窄成
"传输开始后多久没进展"，`--hard-timeout` 才是"等多久放弃"。

### 根因二：管道背压把接收端堵死（测试缺陷）

200MB/1GB 稳定卡在 94%，两端都活着不动，发送端 120 秒后报 `peer idle`。
但**手工用同样参数加 `-q` 跑 200MB 一次通过**（763 块、零重传）。

原因：`Process` 原来用 `subprocess.PIPE`，而测试写法是
`sender.wait_exit(600)` 之后才 `recv.wait_exit(120)` —— 这期间接收端的输出
**没人读**。接收端每 10ms 打一行进度，Windows 管道只有几 KB，写满后接收端
阻塞在 `write` 里，事件循环停摆，不收帧也不回 ACK。两端一起静止。

修法：`Process` 改为子进程 stdout/stderr **直连文件**，`pill()` 按偏移增量读
（用增量 UTF-8 解码器，避免半字符乱码）。文件没有容量上限，读不读只影响断言
实时性。另加 `Cluster.wait_all()` 同时等两端，避免串行等把先失败的一端埋掉。

**教训**：测试脚手架的反压会伪装成产品故障，而且伪装得很像——两端停顿、超时、
日志干净。以后看到"卡在某个百分比"，先确认测试自己在读输出。

### 新增：drop-chunks 场景 + 可观测性

- `relayerd --drop-data-frames 3,5`：测试专用，丢指定的第 N 个转发数据帧
  （只丢 `kChunkRequestData`，控制帧不丢）。启动时打 warning 自曝。
- `TransferPeer::Stats::chunksRetransmitted` → `SendWindow::retransmitted()`
  （累计"取出用于重传的块次"）。
- `relayer-cli --stats`：结论前多打一行 `STATS k=v ...` 契约行。
- 断言：丢 2 块 → `chunksSent=10 chunksRetransmitted=2`。**篡改验证过**：
  改成丢 4 块 → `12 / 4`，证明不是恒真。
