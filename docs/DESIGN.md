# relayer 设计文档

> 本文记录 **relayer 的架构与关键决策**：为什么这样分层、哪些约束不能碰、
> 哪些方案已经否决（以及什么条件下可以改口）。
>
> 线协议以 [`PROTOCOL.md`](PROTOCOL.md) 为**唯一权威**；两者描述同一件事而
> 措辞不同时，以协议文档为准。模块内部的实现细节以代码与注释为准。
>
> 改代码前先读 §2 的硬约束与 §4 的否决清单；要推翻某个决策，先在 §6
> 补一条记录，再动实现。

---

## 1. 定位

跨网络的点对点文件传输工具：一个常驻中继（`relayerd`）、一个 Qt 客户端
（`relayer`）、一个命令行客户端（`relayer-cli`）。目标是**可以公开的开源
项目质量**——陌生人 clone 下来能在几分钟内跑起来，愿意读代码，愿意提 PR。

可验收的六条：

1. **构建简单**：干净 clone 到出可执行文件，三步命令，零手工传参。
2. **依赖可控**：所有三方库 vendored 或标准 `find_package`，版本与许可证
   记在 `third_party/README.md`。
3. **结构清晰**：每个模块职责单一，依赖方向单向，能用一句话说清它做什么。
4. **测试覆盖**：协议、状态机、文件、路径、认证都有自动化测试。
5. **风格一致**：命名、错误处理、日志、注释由工具约束，不依赖个人习惯。
6. **可替换**：文件系统、传输、认证都有接口，能换实现、能 mock。

非目标：

- **不堆特性**。加功能的前提是它解决真实问题，而不是"别家有"。
- **不追求协议向后兼容**——协议可以演进，但不轻易改已实装的帧布局。
- **不做跨平台之外的平台适配**。Windows 与 Linux 为主，macOS 尽力而为。

## 2. 总体架构

### 2.1 分层

```
app/        Qt 前端（唯一允许 #include <Q...> 的地方）
 ├ ui/      .ui + 控件类
 ├ bridge/  Core → Qt 适配层（唯一碰线程与 io_context 的地方）
 └ model/   纯数据模型与纯函数（格式化、进度换算）

core/       通信库，零 Qt
 ├ protocol 帧编解码、消息
 ├ auth     挑战-响应握手
 ├ transport asio 连接、心跳
 ├ session  PeerTable、SessionPolicy、会话内信令
 └ transfer 传输引擎（窗口/ACK/续传/Merkle 校验）

filestore/  文件子系统，零 Qt（core 只看得见 IFileStore.h）
 ├ IFileStore / StdFileStore / MemFileStore
 ├ PathPolicy  路径校验
 └ 归档 tar.xz

common/     最底层：Status + ErrorCode，crypto 原语（SHA-256/HMAC/PBKDF2/AES-GCM）
```

### 2.2 依赖方向（硬约束）

```
app  ──▶ core ──▶ filestore(接口) ──▶ common
 │        │
 │        └──▶ common
 └──────▶ filestore(具体实现，由 app 组装注入)
```

六条规则，由 `tools/check_arch.py` 在 CTest 里变成可执行断言（测试名 `arch`）：

| 规则 | 内容 |
| --- | --- |
| R1 | `core/**` 不得 `#include` Qt 头 |
| R2 | `core/**` 只能 include `IFileStore.h`，不得 include `filestore/` 的具体实现 |
| R3 | `filestore/**` 不得 include `core/` 任何头 |
| R4 | `server/**` 不得 include Qt，也不得 include `filestore/` |
| R5 | `app/` 以外不得 include Qt（`cli/**`、`tests/**` 也要零 Qt） |
| R6 | `common/**` 只能依赖标准库与三方库，不得 include 上层任何模块 |

`app/**` 是唯一允许出现 Qt 的地方。`server/**` 只依赖 `core` + `common`。

### 2.3 产物

| 产物 | 说明 | 依赖 |
| --- | --- | --- |
| `relayer` | GUI 客户端 | core + filestore + Qt |
| `relayerd` | 中继服务端 | core + common（**不需要 filestore，不需要 Qt**） |
| `relayer-cli` | 命令行客户端 | core + filestore |
| `relayer-tests` | 单元/集成测试 | 全部 |

关键点：**服务端不链接 Qt，也不链接文件系统**。它只做认证与转发（见 §3.1）。

## 3. 关键决策

### 3.1 服务端只做转发

`relayerd` 不理解文件：不读写用户数据、不打包、不校验内容、不缓存分片。
它知道的只有「谁在线」「这条帧该往哪条连接倒」。

由此产生的三条硬性约束：

1. **`server/` 不链接 `filestore`**（§2.2 的规则）。不是"暂时不用"，而是永远
   不用——一旦允许，转发层迟早会被塞进"顺手校验一下"的逻辑。
2. **服务端进程的工作目录里不产生任何用户数据文件**。日志除外，且日志路径
   可配置、可关闭。
3. **端到端校验由两端自己做**。服务端无法伪造校验通过，也不会因自己的磁盘
   问题导致传输失败。

换来的三件事：

- **安全面小**：服务端被攻破时不持有用户数据，也没有可被路径穿越利用的文件
  操作入口（服务端根本不碰归档）。
- **部署简单**：无状态、无磁盘依赖，可以跑在只读文件系统的容器里，也可以
  多实例水平扩展（会话粘滞即可）。
- **可审计**：要确认"服务端真的没偷看我的文件"，读一遍 `server/` 就够了。

代价必须写明，避免以后被当成 bug：

- **不支持离线投递**：服务端无处暂存，双方必须同时在线。
- **服务端无法校验完整性**：损坏只能由接收端发现并请求重传。
- 大文件经过带宽不足的中继会变慢——物理限制，不是实现问题。

### 3.2 客户端标识是稳定身份

**id 代表"运行该软件的人"，不是"这一次连接"。** 它必须满足三条：

1. 由用户决定（可固定），跨重连、跨重启不变；
2. 全局唯一——同一个 id 同时只能有一条在线连接；
3. 冲突时**明确失败**，绝不静默改名、绝不顶掉先到者。

第 3 条是关键：自动改名会让对照表在用户不知情的情况下指向另一个人。
宁可连不上，也不能连错。

**动机是防事故，不是洁癖。** 对照表的每一行都存着"发给哪个对端 id"，真实
用法是"这个文件固定发 A、那个固定发 C"，并且需要事后核对发对了人。id 一旦
漂移，结果只有两种：文件发错人；或者指向不存在的连接，服务端静默丢帧，
发送方等满应答超时才报错——用户只看到"卡了很久然后失败"，看不出是 id 的
问题。

实现（线格式与 status 码见 `PROTOCOL.md` §11.7）：

- 客户端认证后发 `kClaimId`(134) 声明自己叫什么；服务端校验合法性 → 检查
  占用 → 迁表改名 → 用 `kAnswerId` 回显最终 id。
- 撞名回 `status=2` 后**由客户端自己断开**：服务端先应答再 close 会丢应答
  （`close` 清空写队列），客户端就分不清撞名还是网络故障。
- 不声明 id 的客户端仍由服务端分配 `client-<n>`——临时用一次 CLI、e2e、
  第三方接入不该被强制先起名。
- `--id` 的语义是**声明**，不是断言：被占用则连接失败，对得上不是前提。
- **别用 `kDirectRequestId`(550) 干这个**——那是 P2P 直连段保留的号。

**自投**（发给自己）是这条决策的自然延伸：对照表里某行的对端恰好是本机 id 时，
帧绕回本连接而不是被拒绝（`PROTOCOL.md` §11.3.1）。客户端不需要特判：入站帧
靠 `sessionId` 解复用，`from` 仍绑定真实身份。

### 3.3 一条连接承载全部操作

一个客户端进程**只维持一条 TCP**：常驻接收会话 + 在其中复用发送、列举、取回。
所有帧靠 `sessionId` 解复用。

为什么不做"控制连接 + 数据连接"：

- 两条线在 NAT/防火墙后面要两条出站，部署成本翻倍；
- 每条线各自有握手与 id，两个 id 之间的关系又是新的状态机；
- 真要克服队头阻塞，代价更小的是"小块 + 写队列优先级 + 单帧写超时"
  （`PROTOCOL.md` §9.4.1 有完整评估）。

具体表现：

- 连接/刷新/发送/列举/取回**全部搭在常驻接收会话上**，id 只分配一次。
- 「点一次刷新，id 涨一号」是这条决策的回归红线：任何"用完即弃"的临时连接
  都会顶掉常驻会话。
- 唯一的例外是 **批量并发发送**：多任务各自新建连接（`kConcurrency=3`，
  同一对端仍串行）。并发与"id 稳定"在这里冲突，选择的是"并发时不换
  常驻会话的 id"——常驻会话不受影响，临时连接只是多发几条。
- 单个大文件在一条 TCP 上串行，不并行分片：并行分片会引入分片调度与乱序
  重排，收益在千兆以内不明显。

### 3.4 分块、窗口与背压

- **默认块 256 KiB，上限 4 MiB**。块大小只决定"控制帧最坏等多久"，吞吐由
  **在飞字节数**决定（`windowBytes = 4 MiB` 换算成块数）。改块大小必须同时
  确认每块固定开销已被消掉，否则吞吐腰斩。
- **"大块吞吐更高"在单 TCP 上是错觉**：真正影响吞吐的是每块的固定开销
  （Windows 上每块 open/close 一次文件实测 ≈ 9 ms，1024 块就是 9 秒）。写盘流
  要整段复用，在锁内 seek/write/flush。
- **控制帧插队**：`isBulkFrame()` 为假的帧排到写队列头部，避免一个大块把
  心跳/ACK 压住几百毫秒。
- **背压靠窗口上限**，不靠"提交时阻塞"。队列满时 `submit()` 返回失败让调用方
  自己决定，而不是把一个线程卡在条件变量上——那正是要避免的事。
- **单帧写超时 60 秒**：接收方消失时不能让写操作永远挂着。

### 3.5 续传与残片校验

- 先落盘后 ACK；`.relaypart` + 原子替换，目标文件要么是旧的完整版、要么是
  新的完整版。
- `ackThrough` 是**最长连续前缀**，不是"最后收到的 + 1"。写成后者在乱序时
  会直接丢数据且不报错——长度对得上、内容错位，只有哈希能发现。
- 续传点不能只按长度信任：预置的残片可能是伪造的。校验用**分块 Merkle 树**，
  能定位到具体是哪一块坏了并只重传那些块，而不是全量重来。
- 完成应答 `kFileAnswerComplete` 的 `status == 0` 表示**已经原子替换完成**，
  不是"打算替换"——提前应答会让发送方删掉源侧状态，而此时目标文件还不存在。

### 3.6 文件子系统：接口 + 多实现

`IFileStore` 是 core 唯一认识的文件抽象（core 只 include 这个头）。实现有
`StdFileStore`（标准库）与 `MemFileStore`（测试用内存盘）。

**路径校验只剩一条线**（2026-10-29 起，见 §6 决策记录）：

- **条目名**：普通列举回来的名字必须是**单段**（不含 `/`、不是 `.`/`..`、非空）。
  解码层整份拒绝而不是跳过单条——半个列表比没有列表更危险。根列表例外，
  靠应答头的 flags 显式标记（那里的名字就是完整路径）。
- **绝对路径**：远端访问没有共享根这一层沙箱（§3.3）。`resolveWithin`
  仍然存在，但只服务"发送方给相对落点"的那条老路径。

**归档（tar.xz）**：

- 打包侧 `sanitizeEntryName` 逐段检查：含 `..`、带盘符（`C:` 与 `C:x` 两种
  形式）、清洗后为空 → 拒绝并记进 `skipped`。前导斜杠不拒绝，收成相对路径。
- 解包侧每个条目走 `resolveWithin`，失败则跳过（记 `skipped`），不整体失败。
  符号链接条目一律跳过：Windows 上建链接要额外权限，链接目标本身也是逃逸点。
- 两种长名字（PAX 与 GNU `'L'`）都认：只认一种的话，系统 `tar` 打的包在我们
  这里长路径会被静默截断到 100 字节，两个深路径塌成同一个名字互相覆盖。
- 流式落盘，不写临时 tar：先打 tar 再压要把整包数据走两遍盘。

### 3.7 Qt 前端的边界

- **UI 布局不动，控件逻辑重写**。`.ui` 从既有设计原样搬迁（只改 `<class>`
  名），排版零改动；控件内部逻辑（状态机、筛选、投影、持久化）重写。
- **`bridge/CoreService` 是唯一的 Qt↔core 边界**：它持有 `io_context` 与
  io 线程，对 `cli::Client` 的调用全部 `asio::post`，回调里 emit Qt 信号
  （跨线程 queued）。控件不碰网络、不碰线程。
- **不要在 onDone 回调栈里析构 `Client`**：`finish()` 返回后仍会访问自己的
  成员。释放点只有两处——下一次操作时替换、或析构（此时 io 线程已 join）。
- **浏览面板一套 UI、两个数据源**：本地同步读盘，远端异步等信号。差异收敛在
  `Source` 枚举上，表格/排序/筛选/导航/拖拽全部共用。
- **异步操作必须留可见结果**：状态行写「读取中 / 共 N 项 / 失败原因」。
  失败与"没反应"在界面上必须能区分。

### 3.8 全路径访问，没有共享根

远端列举、取回、打包、以及发送落点，一律用**对端视角的绝对路径**。
`C://照片`、`/home/me/doc` 直接写，不再有"先配置共享目录再浏览"这一步。

**为什么**：这是单用户自用工具，v1 就是全路径访问。多一层根的实际代价是
每次换目标目录都要改配置 + 断开重连（会话启动时已拷走配置副本），而收益
只在"多个人共用一个中继"时才存在——那种部署本来就不该用这个工具。

**代价写在明面上**：任何能连上中继、知道本机 id 的人，都能列举并取回
本机任意路径的文件（`PROTOCOL.md` §11.8.1）。这不是"疏漏"，是取舍——
部署上必须落实"中继只给自己用"。

**根列表**：绝对路径模型下必须有一个起点，否则请求方只能猜盘符。约定
空路径 = 要根列表（Windows 各盘符根 + 家目录，Unix `/` + 家目录），由
`IFileStore::roots()` 提供。

**发送落点**：`TransferDesc::root` 是绝对路径时直接落那里，不再拼接收
目录。相对路径仍然按接收目录 + `resolveWithin` 解析——CLI 的 `send` 与
"发到对方接收目录"这条老路径靠它。

**发送前的覆盖决策**（`PROTOCOL.md` §11.11）必须在**传输开始之前**完成：
把弹窗塞进 `TransferPeer::handleSendRequest` 会阻塞 io 线程，心跳
（空闲 20s ping、10s 未答判死）跟着停摆，只能加"用户还没点就超时"的
兜底——那比不弹更糟。所以做成一批路径一次问完，拿回结果后在普通模态
对话框里逐项问。

## 4. 已否决的方案

每条都写清"为什么不做"和"什么条件下可以改口"。没有改口条件的，就是不做。

### 4.1 P2P 直连

**不做。** 帧号 550/551 保留未实现（`kDirectRequestId` / `kDirectAnswerId`），
别复用成别的意思。

理由：收益只在"两端同局域网且中继带宽不足"时存在，而代价是一整套 NAT 穿透、
地址交换、直连失败回退、直连信任模型。当前的使用场景（跨网段传文件）里中继
就是链路本身，P2P 只是把同一条链路换成另一条。

改口条件：出现明确的中继带宽瓶颈、且用户能接受配置端口映射。

### 4.2 控制/数据双连接

**不做。** 见 §3.3 的完整理由。评估过的替代方案（小块 + 写队列优先级 + 单帧
写超时）已实装，收益观测不到差异。

改口条件：出现"单条 TCP 的队头阻塞导致可测的功能损坏"，而不是"理论上更优雅"。

### 4.3 BaseAskDF 式的文件访问抽象

**不做。** 浏览面板保留 `Source` 分支，不抽成"本地/远端两个子类 + 工厂"。

1. 那条路抽象掉的是"文件操作"，而方向语义（上传/下载、拖拽源与目标）仍靠
   类型判断——"消灭类型判断"是伪目标。
2. 它的同步签名靠在工作线程里 `promise` + `future.get()` 阻塞，配模态等待框。
   在异步模型里照抄等于把"不阻塞 + 状态行渐进反馈"退回去。
3. 分支里多数是路径语义（home/parent/join/display），该写成普通私有函数，
   不需要类层次；真正需要抽象的 IO 分支只有一处。
4. **没有第二个消费者**。两个实现、一个调用方，还挤在同一个文件里；抽象的
   价值来自多实现 + 多调用方。

改口条件：出现第三种浏览源（归档内预览 / SFTP）；或需要同一面板内跨源拖拽
（那才是这套抽象真正发光的地方）。

### 4.4 4 MiB 大块

**不做默认值。** 上限保留 4 MiB 供调试，默认 256 KiB。

理由见 §3.4：块大小只影响控制帧的最坏等待时间，不影响吞吐；把默认值调到
4 MiB 只会让心跳和 ACK 多等十几倍，而吞吐一点不涨。

改口条件：把每块固定开销压到可忽略之后，仍然测出块大小是瓶颈。

## 5. 工程标准

### 5.1 命名与风格

- 类型 `PascalCase`，函数 `camelCase`，成员 `trailing_`，常量 `kPascalCase`。
- 头文件 `#pragma once`。
- 统一 `.clang-format`（基于 LLVM，Allman 大括号，120 列，4 空格）。
- 不用 `using namespace`。

### 5.2 错误处理

- **跨模块边界不用异常**：文件、网络、协议错误全部走 `Status` + `ErrorCode`
  （`common/include/relayer/common/Status.h`）。
- 异常只允许出现在"解析外部不可信数据"的内层，且必须就地捕获。
- 每个 `catch` 都要有日志，不允许静默吞掉。

### 5.3 日志

- `spdlog`，分级，格式统一。
- **库代码不输出到 stdout**；日志由调用方配置。
- 关键路径（握手、任务开始/结束、重传、回退）必须有日志。

### 5.4 测试

- 框架 Catch2（vendored）。
- 单测：纯函数、状态机、路径、编解码。
- 集成：三进程端到端（`tests/e2e/run_e2e.py`，覆盖正常传输、中断、伪造残片、
  乱序丢包、空文件、目标占用、固定 id、自投、远端列举/取回/打包等场景）。
- 文档一致性也进 CTest：`protocol_doc` 逐项比对 `PROTOCOL.md` 与 `Frame.h`，
  `transition_doc` 比对状态转移表。**加帧类型忘了改文档，测试会红。**
- CI：Windows + Linux，Debug + Release 双跑，**仅 `v*` tag 触发**（日常 push
  跑全量跨平台构建耗额度，收益低于本地 `ctest`）。

### 5.5 提交规范

- Conventional Commits：`feat:` `fix:` `refactor:` `docs:` `test:` `build:`
  `chore:`。
- 一个提交一件事，能编译，提交前跑一遍 `clang-format` 与 `ctest`。
