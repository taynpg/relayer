# relayer 帧协议（RFM1）

> 本文是 relayer 线协议的**唯一权威说明**。实现见 `core/src/protocol/Frame.cpp`，
> 但读到本文就应当能写出一个能互通的服务端或客户端，不需要读代码。
>
> 协议版本：`2`
>
> 版本号只在自己这一侧能判断"对面是不是同一代协议"时才有意义：`version != 2`
> 一律 `kProtocolError` 并断开（§5.3）。将来若要并行支持两代协议，应当把
> version 提到 3，并为旧版本保留一条"拒绝并提示升级"的独立路径——而不是在
> 同一版本号下猜对方的能力。

---

## 1. 设计边界

### 1.1 这个协议做什么

在两个对等端之间（或客户端与中继服务端之间）传**带路由信息的定长头 + 变长载荷**的帧。

### 1.2 这个协议不做什么

- **不做可靠性**。它假定底层是 TCP（或语义等价的可靠有序流），不重传、不排重、不乱序重排。
- **不做分片**。一帧要么完整到达，要么还没有；分块由上层传输引擎负责（见 §8）。
- **不做向前兼容的协商**。版本号不匹配直接断开（见 §5.3），不做能力协商。
- **不含时间戳**。所有依赖时间的判断（超时、nonce 有效期）都在连接层做，
  协议层只保证字节正确。

### 1.3 字节序

**全部字段小端（little-endian）**，与主机字节序无关。

`magic` 是唯一例外需要说明的：它按"字节序列 `R`,`F`,`M`,`1`"定义，
按小端读成 `u32` 时值为 `0x314D4652`。这两个说法等价，实现时按字节序列写更不容易错。

## 2. 帧布局

### 2.1 固定头（36 字节）

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|-----:|-----:|------|------|------|
| 0 | 4 | `magic` | bytes | 固定 `52 46 4D 31`（ASCII `RFM1`） |
| 4 | 2 | `version` | u16 | 当前为 `2` |
| 6 | 2 | `flags` | u16 | 见 §3 |
| 8 | 2 | `type` | u16 | 帧类型，见 §4 |
| 10 | 2 | `reserved` | u16 | **必须为 0**。将来启用需提升版本号 |
| 12 | 8 | `sessionId` | i64 | 会话标识，同一连接可并行多个会话 |
| 20 | 8 | `index` | i64 | 帧序号，语义随 `type` 变化（见 §2.3） |
| 28 | 4 | `frameLen` | u32 | **整帧**字节数，含这 36 字节头 |
| 32 | 4 | `headerCrc` | u32 | CRC32 of bytes `[0, 32)` |

`headerCrc` 覆盖偏移 `0..31`，即**不含 `headerCrc` 自身**的那部分头部。

### 2.2 载荷

紧跟固定头，依次是三个带长度前缀的路由字段，然后是 body：

```
offset                          size       field
.frameLen relative
+0                              1          fromLen   (u8)
+1                              fromLen    from      (UTF-8, 不保证 NUL 结尾)
+1+fromLen                      1          toLen     (u8)
+...+toLen                      toLen      to        (UTF-8)
+...                            1          fuuidLen  (u8)
+...+fuuidLen                   fuuidLen   fuuid     (UTF-8)
+...                            bodyLen    body      (原始字节)
+bodyLen                        [4]        bodyCrc   (u32，仅当 flags 置了 kFlagBodyCrc)
```

`bodyLen = frameLen - 36 - 3 - fromLen - toLen - fuuidLen - (带 bodyCrc ? 4 : 0)`

三个路由字段各自上限 **255 字节**（长度前缀是 u8）。超长**不截断**，打包直接失败——
截断会把两个不同的 id 合成一个，比失败危险得多。

### 2.3 `index` 的语义

| 帧类别 | `index` 含义 |
|--------|-------------|
| 分块数据 / 确认帧 | 块号（从 0 开始） |
| 请求 / 应答帧 | 请求号；应答与对应请求同号 |
| 认证帧 | 恒为 0 |
| 其余控制帧 | 恒为 0 |

接收方**不应**用 `index` 做去重——去重是传输引擎的职责，不是协议的。

## 3. 标志位

| 位 | 名称 | 含义 |
|---:|------|------|
| 0 | `kFlagFromReceiver` | 该帧由「接收文件数据的一侧」发出 |
| 1 | `kFlagEncrypted` | body 已加密，布局见 §6 |
| 2 | `kFlagBodyCrc` | body 尾部附带 u32 CRC32 |

### 3.1 `kFlagFromReceiver`

发送侧与接收侧各自维护一份会话槽。这个位决定去哪个槽找会话。

**不要**用 `flags != 0` 判断方向。方向与加密挤在同一个字段的不同位上时，
"按非零判方向"在加上加密位之后就会取错槽——这是把两者显式拆开的直接原因。

### 3.2 `kFlagBodyCrc` 由谁决定

**由打包方根据 body 长度自动决定，调用方不能自己置位**：

- `body.size() <= 65536`（`kBodyCrcLimit`）→ 置位并写 CRC
- 否则 → 清除该位，不写 CRC

原因：大块数据的完整性由传输层的分块 Merkle 校验保证（§8.3），每帧多加 4 字节
收益很小；而且"带不带 CRC"会影响 `bodyLen` 的计算，让它依赖调用方的意志会让
解包侧的验证逻辑变复杂。

解包侧必须**相信标志位而不相信自己的推测**：带就校验，不带就不校验。

### 3.3 `kFlagEncrypted` 与 body CRC 的组合

两者可以同时置位。此时 `bodyCrc` 计算的是**密文**的 CRC，不是明文的。

理由：解包方在拿到帧的那一刻还没有密钥协商结果（或不想为了校验而解密），
用密文 CRC 可以先做一层廉价筛查，再解密。反过来若用明文 CRC，解包方不解密就
无法验证，等于白占 4 字节。

## 4. 帧类型

类型号是线格式的一部分，**发布后不可更改**。分段是为了让接收方能便宜地判断

| 号段 | 用途 | 备注 |
|------|------|------|
| `0 .. 99` | 握手与认证 | 认证三段 + 心跳 |

## 5. 解包算法

### 5.1 三态返回

解包函数返回三种结果之一：

| 结果 | 含义 | 调用方动作 |
|------|------|-----------|
| `kOk` | 解出一帧 | 消费 `consumed` 字节，处理帧 |
| `kNeedMoreData` | 输入不够 | 消费 `consumed` 字节，保留剩余，等更多数据 |
| `kProtocolError` | 流已不可恢复 | **断开连接** |

`consumed` 的语义在三种情况下都不同，必须严格按上表处理。

### 5.2 步骤

```
1. 找 magic
   从起始位置逐字节前进，直到找到 4 字节的 "RFM1"。
   - 没找到完整 magic：丢弃 avail-3 字节（末尾最多 3 字节可能是半个 magic），
     返回 kNeedMoreData
   - 找到了但不是第 0 字节：丢弃 magic 之前的垃圾，返回 kNeedMoreData
     （让调用方从 magic 处重新进来，实现更简单）

2. 固定头是否收全
   avail < 36 → kNeedMoreData，consumed = 0

3. 头部 sanity + CRC

   frameLen 不在 [39, 32MB] 内  → 跳过 1 字节，回到步骤 1
   headerCrc 不匹配               → 跳过 1 字节，回到步骤 1
   version != 2                  → 返回 kProtocolError
   avail < frameLen              → kNeedMoreData，consumed = 0

4. 拆路由字段
   三次 (u8 长度 + 内容)。任一次字段越界 → 跳过 1 字节，回到步骤 1

5. body 与 CRC
   带 kFlagBodyCrc 时校验；不匹配 → 丢掉整帧，返回 kProtocolError

6. 类型合法性
   type 落在未定义区间 → 丢掉整帧，返回 kProtocolError

7. 填帧，consumed = frameLen，返回 kOk
```

### 5.3 为什么"头 CRC 不对"和"版本不对"处理方式不同

- **头 CRC 不对**：最可能是 body 里恰好出现了 `RFM1` 四个字节（压缩数据、
  随机二进制里很常见）。这是**误判**，流本身没问题，所以跳 1 字节继续找。

- **版本不对**：头部 CRC 都对上了，说明对端确实是按协议打的包，只是版本号不同。
  这时候继续扫下去只会把整条流都当成垃圾，永远不会成功。所以直接报协议错误、
  让调用方断开并提示用户升级。

这个区分是有意的：误判不该导致断开，版本不符必须立刻断开。

### 5.4 重同步的代价

最坏情况下（每 4 字节就出现一次假 magic 且 CRC 都不对），每前进 1 字节要做一次
32 字节 CRC 计算。32MB 的流最坏是 32768 次扫描，每次 32 字节 CRC —— 约 1 毫秒量级。
可以接受，不需要更复杂的同步策略。

### 5.5 空 body 也带 CRC

`bodyLen == 0` 时 `0 <= kBodyCrcLimit` 成立，所以空 body 的帧也会带 4 字节 CRC。
因此线上**实际最短帧是 43 字节**（36 + 3 + 4），而不是理论的 39 字节。

`kMinFrameSize = 39` 只是"不带 CRC 时的理论下限"，用于步骤 3 的范围检查。

## 6. 加密载荷布局

> **状态：布局已定，尚未实装。** 帧头保留了 `kFlagEncrypted` 位与下面的载荷
> 布局，但当前的发送路径不加密（不置位），也没有密钥协商流程。读到本节时
> 不要假设线上数据是加密的——**认证**是实装的（§7），**保密**不是。
>
> 实装时要补的第一件事不是加解密本身，而是密钥协商：`nonce` 的唯一性靠
> 会话密钥保证，而会话密钥必须先安全地建立起来。

当 `kFlagEncrypted` 置位时，`body` 的布局是：

```
nonce[12] || ciphertext[N] || tag[16]
```

- 算法：AES-256-GCM
- `nonce`：12 字节，**每次加密必须唯一**（同一密钥下复用 nonce 会直接泄露明文异或值）
- `tag`：16 字节完整长度，不支持截断
- AAD：见 §6.1

### 6.1 AAD 用什么

AAD 参与认证但不加密，因此可以把"必须被保护、但不需要保密"的元数据放进去，
防止攻击者篡改它们而不被发现。本协议约定 AAD 为：

```
AAD = magic[4] || version[2] || flags[2] || type[2] || sessionId[8] || index[8]
```

也就是固定头的前 28 字节（不含 `frameLen` 与 `headerCrc`）。

这样攻击者即使重算 `headerCrc` 把 `type` 从 `kAskDelete` 改成 `kAskFileList`，
解密时 tag 也校验不过。

**`frameLen` 故意不在 AAD 里**：它是长度，改它会导致帧边界错乱，
在 TCP 层就会表现为解析失败，不需要 GCM 再保护一次。

## 7. 认证握手

### 7.1 时序

```
client                                          server
  │ ── TCP connect ──────────────────────────────▶│
  │◀── Challenge(salt[16], nonceS[32]) ───────────│
  │                                               │
  │   key   = PBKDF2-HMAC-SHA256(pw, salt, 20000, 32)
  │   proof = HMAC-SHA256(key, tag ‖ nonceS ‖ nonceC)
  │                                               │
  │── Response(nonceC[32], proof[32]) ───────────▶│
  │                                               │  校验 proof
  │                                               │  serverProof =
  │                                               │    HMAC(key, tag ‖ nonceC ‖ nonceS)
  │◀── Result(ok, serverProof[32]) ───────────────│
  │                                               │
  │  校验 serverProof                              │
  │── AskId ... ─────────────────────────────────▶│  此后才受理业务帧
```

`tag` 是一个固定的域分隔字符串，取值见 §7.3。

### 7.2 `status` 取值

| 值 | 名称 | 含义 |
|---:|------|------|
| 0 | `kOk` | 成功 |
| 1 | `kBadProof` | proof 不匹配（口令错） |
| 2 | `kReplay` | nonce 重复（重放攻击） |
| 3 | `kUnsupported` | 版本或算法不支持 |
| 4 | `kInternal` | 服务端内部错误 |

认证失败时**不要**区分"口令错"和"用户不存在"——那会给攻击者提供用户枚举能力。
本项目没有用户概念（只有一条共享口令），所以这条约束天然满足，但扩展时要注意。

### 7.3 域分隔 `tag`

```
tag = "relayer/auth/v2"        // 15 字节（ASCII，无 NUL 结尾）
```

作用是把这次 HMAC 与"任何其他用到同一密钥的 HMAC"区分开。没有它的话，
如果将来某个环节也用 `key` 做 MAC，攻击者可能把两个场景的输出互换。

### 7.4 为什么两个 proof 的 nonce 顺序相反

```
clientProof = HMAC(key, tag ‖ nonceS ‖ nonceC)
serverProof = HMAC(key, tag ‖ nonceC ‖ nonceS)
```

顺序相反保证**两个 proof 一定不相等**，否则一个中间人可以截获客户端发的
proof 然后原样回给客户端，冒充服务端。

### 7.5 nonce 与重放

- `nonceS` 由服务端每次连接生成（建议 CSPRNG），32 字节
- `nonceC` 由客户端每次连接生成，32 字节
- 双方都应当**记住最近收到的 nonce**，拒绝重复值

只靠时间窗口不够：攻击者可以在窗口内重放。必须维护一个已见 nonce 集合，
或者用单调计数器（本项目用随机 nonce + 集合，因为连接数不大）。

### 7.6 `authEnabled = false` 的降级

服务端可以配置成不认证。此时：

- 不发 `kAuthChallenge`，连接建立后直接受理业务帧
- 客户端如果配置了期待认证却收到业务帧，应当报错而不是静默降级

**降级只允许由服务端配置显式开启**，不允许"因为握手失败所以跳过"——
那等于把认证变成可选项。

## 8. 传输状态机

### 8.1 状态

```
Idle → Handshaking → Transferring → Finalizing → Done
                   ↘ Interrupted → (Resume) → Transferring
```

| 状态 | 含义 |
|------|------|
| `Idle` | 连接已建立，未开始任何会话 |
| `Handshaking` | 认证握手中 |
| `Transferring` | 正在传数据块 |
| `Finalizing` | 数据发完，等最终校验与落盘确认 |
| `Interrupted` | 中断（网络、用户取消、对端消失），可续传 |
| `Done` | 成功完成 |

### 8.2 事件与转移

| 从 | 事件 | 到 |
|----|------|----|
| `Idle` | `StartHandshake` | `Handshaking` |
| `Handshaking` | `AuthOk` | `Idle`（已认证，可开业务会话） |
| `Handshaking` | `AuthFail` | `Done`（作废） |
| `Idle` | `StartTransfer` | `Transferring` |
| `Transferring` | `AllChunksAcked` | `Finalizing` |
| `Transferring` | `Interrupt` | `Interrupted` |
| `Finalizing` | `VerifyOk` | `Done` |
| `Finalizing` | `VerifyFail` | `Interrupted` |
| `Interrupted` | `Resume` | `Transferring` |
| `Interrupted` | `Abort` | `Done` |

**其余所有 (状态, 事件) 组合都非法**，必须显式失败而不是静默忽略。

这条规则需要有测试遍历全部组合来保证，不能靠"实现的时候记得"。

实现与校验：

- 代码：`core/include/relayer/core/transfer/StateMachine.h` 的 `kTransitions[]`
- 单元测试遍历 6×10=60 个组合（`tests/core/StateMachineTest.cpp`）
- `tools/check_transition_doc.py` 在本节与代码之间做双向比对，接在 CTest 里

改本节表格或改代码表，任一侧漏改都会让 CI 变红。

### 8.3 分块与增量校验

传输大文件时按块（默认 256 KiB）发送，每块算一个 SHA-256。

- 块内偏移写在 `index` 里（块号）
- 接收方维护块级位图，已收到的块可以乱序落盘
- 全部收完后按块哈希合并成一棵 Merkle 树，树根与发送方事先告知的整文件哈希比对

**先落盘后 ACK**：接收方只有在数据确实写进文件之后才发确认。宁可慢一点，
也不要出现"确认了但重启后文件是坏的"。

中断续传时，接收方把位图发给发送方（SACK），发送方只重发缺失的块。

#### 8.3.1 Merkle 树构造

树必须是**双方都能独立算出同一个根**的规范形式，否则"根相同"什么也没证明。

```
叶子  = SHA256( 0x00 || chunk[chunkIndex] )
节点  = SHA256( 0x01 || 左子 || 右子 )
根    = 逐层两两合并，直到只剩一个节点
```

三条规则需要写死：

1. **前缀字节**：叶子 `0x00`、内部节点 `0x01`。没有这个前缀，就把自己
   套进了"第二原像"问题——攻击者可以把一个内部节点当作叶子内容提交。
   这是 RFC 6962 的做法，照抄即可。
2. **奇数个节点时，最后一个单独上提，不复制**。比特币那样"复制最后一个"
   的做法会导致 `[a,b,c]` 和 `[a,b,c,c]` 得到同一个根，即两种不同的文件内容
   通过同一个校验。
3. **块长不参与叶子哈希**。叶子哈希的是**补齐到 `chunkSize` 的块内容**——
   最后一块不足时按 `chunkSize` 补零后再哈希。理由：`payloadLen` 是可变的，
   若它参与运算，同一份文件在不同块大小下会得到不同根，而"根"应当只由
   文件内容与块大小决定。

空文件（`totalSize == 0`）的根定义为 `SHA256("")`，即
`e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`。
这不是特例漏洞：零个叶子的树只能有一个根，写死一个值比让实现各自
处理"空树返回什么"安全。

只有一个块时，根 = 该叶子的哈希（不再套一层节点）。

**分块 Merkle 树相对"整文件 SHA-256"的额外价值**：整文件哈希只能在传完后
说"错了"，Merkle 树能定位到**哪一块**错了。`kFileAnswerComplete` 返回
`status = 1` 时，双方可以再交换一层的中间哈希，把范围缩小到具体的块，只重传
那一块。这一步本版**未实现**（协议留了位置，实现只做"整棵重传"），因为
默认块只有 256 KiB，整棵重传的代价本来就不高——一次全量重传在常见文件上
也就是多传几秒，而块级定位要引入额外的往返和状态。


### 8.4 `.relaypart` 临时文件

接收中的文件写成 `<目标名>.relaypart`，完成后原子重命名。这样：

- 中断后能识别出"这是个未完成的下载"
- 不会出现半个文件被用户误当成完整文件

### 8.5 心跳与空闲超时

用 §4.2 定义的 `kAskHeart`(124) / `kAnswerHeart`(125)，两者 `body` 都为空。

**为什么不用 TCP keepalive**：keepalive 默认 2 小时才报死，而且只能检测
"连接被中间设备丢弃"，检测不到"对端进程卡死但 socket 还开着"。后者在文件
传输里代价很高——对端卡住十秒可能意味着几百个块白传。

#### 8.5.1 参数

| 参数 | 值 | 含义 |
|------|-----|------|
| `kIdleBeforePing` | 20 s | 连续这么久没收到任何字节，就发一个 `kAskHeart` |
| `kPingTimeout` | 10 s | 发了 `kAskHeart` 之后这么久没有应答，判定对端失联 |
| `kTickInterval` | 1 s | 检查上述两个时间戳的轮询间隔 |

最坏发现时间 = 20 + 10 = 30 秒。

这张表与 `core/include/relayer/core/transport/Heartbeat.h` 里的 `constexpr`
常量一一对应，`tests/core/HeartbeatTest.cpp` 把它们钉死防止被"顺手调一下"。

#### 8.5.2 规则

1. **任何入站字节都算生命迹象**，包括业务帧、`kAnswerHeart`、甚至重同步前
   的垃圾字节。心跳要回答的问题是"对端还有没有反应"，不是"对端是否遵循
   心跳协议"。一个只在发数据的对端显然活着，此时判它超时是错的。
2. **出站动作不算生命迹象**。发 `kAskHeart` 不重置空闲计时器——否则只要
   我们在发包，就永远不会超时，哪怕对端早已断开。
3. **一个未应答的 `kAskHeart` 在路上时，不重复发新的**。重复发送不带来新
   信息，只会让对端收到一串无用帧。
4. **未应答超过 `kPingTimeout` 判失联**，与是否继续有出站流量无关。
5. **收到 `kAskHeart` 必须立即回 `kAnswerHeart`**，该应答属于规则 1 意义上
   的入站字节，同时触发对方的"未应答"标记清除。
6. 超时判定用 `>=` 而非 `>`：恰好落在边界上必须触发，否则会出现"周期
   恰好等于阈值时永远不超时"。

#### 8.5.3 判定顺序

检查动作时**必须先判超时，再判是否该发新心跳**：

```
if 有未应答的 ping:
    if now - 发出时刻 >= kPingTimeout:  → 超时，断开
    else:                               → 什么都不做
elif now - 最后收字节时刻 >= kIdleBeforePing: → 发 kAskHeart
else:                                          → 什么都不做
```

顺序写反会导致已超时的连接继续发新心跳（"空闲超过 20 秒"这个条件在死连接
上恒成立），问题被掩盖成"一直在重试"，永远不断开。

#### 8.5.4 与传输状态机的关系

心跳**不改变** §8.1 的状态。它是连接层的活性检测，`Transferring` 期间同样
生效（虽然那时业务流量通常已让心跳处于静默）。判定超时后的断开动作，由上层
转为 `Interrupt` 事件进入 `Interrupted`，走 §8.3 的续传路径。

实现在 `core/include/relayer/core/transport/Heartbeat.h`，是**纯逻辑**——输入
时间点，输出动作，不做 I/O。这样测试可以把十分钟的行为在微秒内跑完，避免真
`sleep` 造成的 CI 偶发失败。

## 9. 载荷编码约定

以下约定适用于所有 `body` 内的结构（认证段与分块段的裸字节除外）。

### 9.1 通用原则

- 整数小端，宽度显式（`u8` / `u16` / `u32` / `u64`）
- 字符串：`u16 长度 || UTF-8 字节`，**不带 NUL 结尾**
  （路由字段例外，它们用 `u8` 长度前缀，因为上限只有 255）
- 列表：`u32 元素个数 || 元素...`
- 没有"可选字段"：需要可空时用单独的长度 0 表示

### 9.2 文件条目列表（`kAnswerFileList`）

```
u32 count
重复 count 次：
    u8  nameLen,  name[nameLen]        // 仅文件名，不含目录
    u8  type                            // 0=文件 1=目录 2=符号链接
    u64 size
    i64 mtime                           // Unix 秒
    u16 mode                            // POSIX 权限位
```

### 9.3 文件元信息（`kAnswerFileMeta`）

```
u8  status
若 status == 0：
    u8  nameLen,  name[nameLen]
    u64 size
    i64 mtime
    u16 mode
    u8  sha256Len, sha256[sha256Len]     // 十六进制字符串，通常是 64
```

### 9.4 传输会话描述（`kFileRequestSend` / `kFileAnswerSend`）

发起方向接收方描述"要传什么"。接收方要能据此判断"这是不是我以为的那个文件"，
以及"我手上那份残片还有没有用"。

```
u16 descLen,  desc[descLen]       // UTF-8 显示名，仅用于界面与日志
u64 totalSize                     // 文件总长（未压缩）
u32 chunkSize                     // 每块字节数，发送方决定；见 9.4.1
u8  sha256Len, sha256[sha256Len]  // 整文件 SHA-256 的十六进制小写（通常 64）
u8  fingerprintLen, fingerprint[fingerprintLen]
                                  // IFileStore::quickFingerprint 的输出（十六进制）
u16 rootLen,  root[rootLen]       // 落点相对路径，相对接收方 root
```

`fingerprint` 是**断点续传的判据**，不是安全检查。它由 `(总长, 前 64KB,
有效长度)` 算出，能让"同名但内容不同的两个文件"区分开。但它只覆盖前 64KB
——足以挡住"下错文件"，挡不住刻意的构造。真正的完整性由 `sha256` 与分块
Merkle 树（§8.3）保证。

`root` 可以带目录段（如 `docs/manual.pdf`）——这是"发送方指定相对目录"
的正式语义：接收方落点 = 接收根目录 / root / 文件。接收方必须先用路径
校验（等价于 `resolveWithin`：拒绝绝对路径、盘符、逃出根目录的 `..`）
再落盘，且**在打开目标文件之前把中间目录建齐**。相对接收根目录的子目录
由发送方的描述产生，不代表接收方授权发送方写根目录以外的任何位置。

#### 9.4.1 块大小

`chunkSize` 由**发送方**决定并告知，接收方不做协商回退——理由见下面的
"为什么不做双向协商"。

约束：`1024 <= chunkSize <= 4 MiB`，且必须是 1024 的整数倍。违规的请求
一律拒绝（`kAnswerSend` 里 `status = 4`）。

上限 4 MiB 来自帧上限（§3 的 `kMaxFrameSize` 是 32 MiB）与内存的折中：
一个块要在发送侧和接收侧各占一份缓冲，加上帧头和加密膨胀，4 MiB 让"同时
在飞的 8 个块"控制在 32 MiB 以内。

**默认值是 256 KiB，不是上限。** 这一点值得写清楚，因为"块越大吞吐越高"
只在没有交互需求的场景下成立。数据帧和控制帧共用同一条 TCP 连接时，一块
数据要在写队列里被完整写出去，排在它后面的 `kFileRequestCancel` /
`kFileAnswerComplete` 才能出队。4 MiB 块在 1 MB/s 的上行链路上要写 4 秒，
窗口满时最坏十几秒——用户点了取消，界面半天没反应。256 KiB 把这个量级
压到 0.25 秒，代价只是每块多几十字节的帧头。

吞吐由**在飞字节数**而不是块大小决定，所以实现里窗口按字节配额
（默认 4 MiB 在飞）换算成块数，块小时自动变成更多块。传输层另有一条
优先级规则：承载大块数据的两种帧（`kChunkRequestData` /
`kChunkAnswerData`）排低优先级，其余帧排高优先级——这是单连接能做到的
最好程度，也是"不做双连接"的前提。

**为什么不做双向协商**：协商要一轮往返，而"多大块合适"几乎完全由发送方
的读盘速度决定；接收方唯一有意义的反对理由是"我没那么大内存"，那属于
接收方拒绝这个任务，而不是"我们各退一半"。一轮往返换一个大概率相同的结果
不划算。真需要小块时，由接收方在 `kFileAnswerSend` 里带一个上界建议值
（见 9.5），发送方自愿采纳——但仍然由发送方最终决定。

### 9.5 传输应答（`kFileAnswerSend` / `kFileAnswerDown`）

```
u8  status            // 0=接受，非 0 见下表
u64 resumeOffset      // status==0 时有效：从这个偏移开始发
u32 chunkSizeHint     // status==0 时有效：接收方建议的块大小，0 表示"没意见"
u8  sha256Len, sha256[sha256Len]   // status!=0 时可带原因描述，也可长度 0
```

`status` 取值：

| 值 | 含义 | 发送方应当 |
|---:|------|-----------|
| 0 | 接受 | 从 `resumeOffset` 继续 |
| 1 | 拒绝：目标已存在且内容不同 | 询问用户是否覆盖 |
| 2 | 拒绝：磁盘空间不足 | 放弃或换目标 |
| 3 | 拒绝：目标路径不可写 | 换目标 |
| 4 | 拒绝：描述非法（块大小越界、总长与块数不匹配等） | 修正后重试，通常说明有 bug |
| 5 | 拒绝：正在传输同名任务 | 等待或取消旧任务 |
| 6 | 拒绝：文件过大，超出本端上限 | 放弃 |

`resumeOffset` **必须是 chunkSize 的整数倍**。理由：续传按块对齐，非对齐的
偏移会让"块号 → 文件偏移"的映射不再是简单乘法，而那个映射是"乱序落盘"的
基础（§8.3）。接收方发现对齐后的残片小于一个块时，直接当作"没有残片"
（`resumeOffset = 0`），不要为了挽救几百字节去引入非对齐路径。

### 9.6 分块数据（`kChunkRequestData`）

```
u32 chunkIndex        // 块号，从 0 开始
u32 payloadLen
u8  payload[payloadLen]
```

帧头的 `index` 字段**同时**填块号，`sessionId` 填会话。两处都填是刻意的
冗余：`index` 是上一层的通用字段，日志和路由都靠它；body 里再带一份，是为了
让"分块解析"不依赖帧头语义——`body` 自成一体时，离线分析抓包和单测都能直接
处理，不必先构造一个完整帧。

**最后一块可以短于 `chunkSize`**。`payloadLen` 是权威长度，接收方不得假设
它等于 `chunkSize`。反过来，非最后一块**必须**恰好是 `chunkSize`，否则拒绝
——否则"块号 → 偏移"的乘法映射就会被破坏，而错位写入在完成后才表现为
哈希不匹配，极难定位。

### 9.7 分块确认（`kChunkRequestAck` / `kChunkAnswerAck`）

接收方按累积 ACK + SACK 位图回报进度。

```
u32 ackThrough        // 连续收到的块数：块 [0, ackThrough) 全部已落盘
u32 bitmapWordCount
u32 bitmap[bitmapWordCount]   // 从块号 ackThrough 起的位图，bit i = 块 ackThrough+i 已收到
```

`ackThrough` 不是"最后收到的块号 + 1"，而是**最长的连续前缀长度**。差别在
乱序时体现：收到 0,1,5 时 `ackThrough = 2`，位图第 3 位（块 5）置 1。若把
`ackThrough` 写成"最后收到的 +1"，发送方会以为 2、3、4 都到了，直接造成
数据丢失且**不会报错**——文件长度对得上，内容错位，只有哈希能发现。

位图长度由 `bitmapWordCount` 决定，为 0 表示"没有空洞，不用重传"。发送方
必须能处理 `ackThrough` 已经到末尾的情况（此时位图为空）。

**位图按 32 位字打包，低位在前**：位图中的第 `i` 位在 `bitmap[i / 32]` 的
`1 << (i % 32)` 位上。这与 §7 里位标志的约定一致，避免同一份协议里出现
两种位序。

### 9.8 完成握手（`kFileRequestComplete` / `kFileAnswerComplete`）

```
kFileRequestComplete:
    u8  merkleRootLen, merkleRoot[merkleRootLen]   // 十六进制小写，通常 64
    u64 finalSize

kFileAnswerComplete:
    u8  status            // 0=校验通过并已落盘，非 0 见下
    u8  merkleRootLen, merkleRoot[merkleRootLen]   // status!=0 时带本端算出的根
```

| 值 | 含义 | 双方动作 |
|---:|------|---------|
| 0 | 校验通过，已原子替换为目标文件 | 正常结束 |
| 1 | Merkle 根不匹配 | 保留残片，可续传（多半是某块写错位） |
| 2 | 落盘失败（空间/权限/同步错误） | 保留残片，报错 |
| 3 | 块数或总长与描述不一致 | 作废残片，必须全量重传 |

**`status == 0` 是"已经原子替换完成"的意思，不是"我打算替换"**。接收方
必须先把 `.relaypart` 刷到磁盘（`sync`）、算出树根、确认无误，再做原子替换，
最后才回 0。提前应答会让发送方删除源侧临时状态，而此时目标文件还不存在
——这正是"确认了但重启后文件是坏的"的来源（§8.3）。

## 10. 错误处理

### 10.1 协议层错误

| 情况 | 处理 |
|------|------|
| 头部 CRC 不匹配 | 当作误判，跳 1 字节重同步 |
| `frameLen` 越界 | 同上 |
| 路由字段越界 | 同上 |
| 版本不符 | `kProtocolError`，断开 |
| body CRC 不匹配 | `kProtocolError`，断开 |
| 类型号未定义 | `kProtocolError`，断开 |

### 10.2 业务层错误

业务失败**不走**协议错误，走应答帧里的 `status(u8)`。理由：

- 协议错误意味着"这条连接不可信了"，要断开
- 业务错误（文件不存在、权限不足）是正常结果，连接应当继续可用

对应到实现里的 `ErrorCode`（`common/include/relayer/common/Status.h`）：

| `status` | `ErrorCode` |
|---------:|-------------|
| 0 | `kOk` |
| 1 | `kNotFound` |
| 2 | `kPermissionDenied` |
| 3 | `kAlreadyExists` |
| 4 | `kInvalidPath` |
| 5 | `kNoSpace` |
| 6 | `kIoError` |
| 7 | `kUnsupported` |

### 10.3 身份绑定

**服务端必须强制覆写 `frame->from`**，用连接建立时认证过的身份。

客户端在 `from` 里写的任何内容都不可信——否则客户端 A 可以伪造
`from = "B"` 删掉 B 的文件。这条约束在服务端实现，不在协议格式里表达，
因为格式无法表达"必须覆写"这种要求。

落笔只有一个入口：`auth::bindSenderIdentity()`。**不要**手写 `f.from = id`，
那个函数存在的全部意义就是让这条规则世间只有一处实现。

## 11. 会话与转发规则

本节规定一条连接上"哪些帧能过、过了要做什么骨架手术"。实现见
`core/include/relayer/core/session/SessionPolicy.h`，是纯逻辑（不做 I/O）。

### 11.1 相位

每条连接只有一个会话相位，由 §7 的握手决定：

| 相位 | 允许入站的帧 |
|------|-------------|
| 未认证 | 认证帧（0..3）+ 心跳（124 / 125） |
| 已认证 | 全部已定义类型 |

**未认证时收到业务帧必须断开，不能静默丢弃**。理由：能发业务帧说明对端
自认为握手已结束，而我们这边没结束——双方对"走到哪一步"的认知不一致。
静默丢弃会让对端一直重试，这个差异不会自己消失；断开是唯一能让用户立刻
看到问题的方式。

### 11.2 心跳是例外

心跳在认证完成前后**都应被应答**，因为它检测的是"这条 TCP 连接还活着"，
与身份无关。

这个例外的价值在于把两种故障区分开：

| 现象 | 结论 |
|------|------|
| 心跳超时（§8.5） | TCP 断了，或对端进程死了 |
| 心跳正常但认证不完成 | TCP 通，问题在握手（口令、版本、实现） |

如果未认证时不答心跳，第二种会表现成第一种，排查方向直接跑偏。

### 11.3 转发

服务端收到一帧后按 `to` 决定去向：

| `to` | 去向 |
|------|------|
| 空 | 本地受理（发给服务端自己） |
| 等于服务端 id | 本地受理 |
| 等于发送者自己的 id | **转发回这条连接**（自投，见下） |
| 其他 | 转发给 `to` |

**`to` 为空算本地受理**，不是"无法投递"：客户端在拿到自己的 id 之前
根本不知道服务端叫什么（`kAskId` 就是用来问这个的），要求它先填 `to`
会形成鸡生蛋问题。

**"等于发送者自己的 id" 里的发送者身份必须来自认证阶段，不能读 `from`。**
`from` 是对端自称的，它可以随便写别人的名字——若拿它做这个判断，攻击者
只要把 `from` 写成自己的名字，就能让本该转发的帧被本地受理。

#### 11.3.1 自投（发给自己）

**一个实例把文件发给自己**，用途是**本机自测**：一条命令即可验证中继、
认证、传输、落盘整条链路，不必找第二台机器。语义就是上表那一行：
`to == 发送者自己的 id` 时，服务端把帧**转发回发送者所在的那条连接**。

| 项 | 规则 |
|----|------|
| 路由 | 走正常的 `kForward`，目标是发送者自己的连接 |
| `from` | 仍是发送者的真实身份（与转发他人完全一致，`forward()` 负责绑定） |
| 客户端 | 必须能收下 `from == 自己 id` 的帧（与收别人的帧没有区别） |
| 服务端 | 不做特判以外的任何事，也不缓存 |

**为什么不是"本地受理"**：本地受理意味着交给服务端处理，而服务端不做
文件业务（`DESIGN.md` §3.1），帧会凭空消失——比明确拒绝更难排查。
**为什么不是"拒绝"**：早期版本拒绝，理由是"只可能是拼错了 `to`"。那是
把猜测当成规则——用户真的会这么用（自测），而拒绝会把一个合法场景变成
"发送方等满应答超时"。

**安全性**：`selfId` 来自认证阶段而非 `from`，发送者只可能把帧绕回自己，
偷不到别人的帧、也干扰不到别人；转发时 `from` 仍被绑定成真实身份，
伪造路径未被打开。唯一的代价是服务端多转发一份自己发给自己流量。在
同一连接上，接收端与发送端靠 `sessionId` 解复用（§9.4.1），不会串台。

### 11.4 出站侧的身份断言

服务端会发出三类帧，`from` 的合法取值各不相同：

| 帧的来源 | 合法 `from` |
|----------|-------------|
| 服务端主动发起（应答、通知） | 空，或服务端自己的 id |
| 本地受理后由业务层回复 | 空，或服务端自己的 id |
| **转发他人的帧** | 恰好是该帧**发送者**在认证时得到的 id |

前两类的断言是"不许出现第三方身份"：

> 服务端发出的帧，`from` 要么为空（不代表任何客户端），要么等于服务端
> 自己的 id。

原因是：转发时若漏了覆写，帧会带着发送方的自称身份原样出去，而入站侧
的检查**拦不住**这种情况（入站时 `from = "alice"` 完全合法）。这种失败
模式在功能测试里看起来完全正常——只是身份是错的——所以必须有一个显式的
拒绝点。

第三类必须单独说明，否则上面那条断言会把**正确的转发**也一起拒掉——
转发后的 `from` 恰恰是别人的 id。转发路径的合法集合是"发送者在认证时
得到的 id"，而不是"空或服务端 id"。

这两个集合互不相交（转发帧的 `from` 一定不是服务端 id），所以判定时
**必须显式区分"这是转发帧"还是"这是我自己的帧"**，不能只看 `from` 的值。
实现上由 `planRoute()/forward()` 与 `send()` 两个入口分开，调用方不需要
自己判断属于哪一类。

客户端的出站不做此检查：它只能代表自己，越权的那一步在服务端入站侧覆盖。

### 11.5 在线对端表

服务端维护一张"id → 在线连接"的表，用来把 `to` 字段翻译成"从哪条连接
发出去"。实现见 `core/include/relayer/core/session/PeerTable.h`，同样
是纯逻辑，不认识 `Session` 也不认识 asio。

表里每条记录只有两样东西：`id` 和展示用的地址（`"ip:port"`）。**刻意
不存 `Session` 指针**——这张表要能被 UI 和日志安全读取，暴露裸指针会
诱使调用方绕过相位检查直接发帧。

| 操作 | 规则 |
|------|------|
| 注册 | 空 id 拒绝；重名拒绝（**不顶掉**原记录）；满容量拒绝 |
| 注销 | 返回"是否真的删掉了"，不是静默成功 |
| 查找 | 返回的指针在下一次增删前有效，**不得跨异步边界保存** |
| 列表 | 返回副本，按 id 字典序 |

三条规则值得单独说明理由：

**重名不顶掉先到者。** 顶掉等于允许后来者把先到者踢下线，而"谁是真的"
不该由一次 id 冲突隐式决定。要让新连接占据某个 id，调用方必须先显式注销
旧连接。

**注销不做静默幂等。** 调用方需要知道这次注销是不是真的发生了，因为它
决定了要不要广播"有人下线"。把重复注销做成静默成功，会让重复通知变成
常态，而重复通知在客户端侧表现为列表闪烁。

**列表顺序稳定（字典序，不是哈希序）。** 连接数在几十到几千量级，
`std::map` 的 O(log n) 完全够用；它换来的是"客户端列表不会因为重哈希而
乱跳"，这直接决定 UI 上"谁上线了"看起来是否可靠。

容量默认 1024。有上限的理由与帧缓冲上限一样：id 由客户端声明（§11.7）
或服务端分配（§11.6），不设限的话一个循环重连的 bug 客户端就能把表撑到吃光内存。

### 11.6 id 分配与 `kAnswerId`

认证完成后，服务端为对端确定一个 id，然后**主动**发 `kAnswerId` 告知
（不等客户端请求）。

选择主动告知而不是纯请求-应答，是因为请求-应答会让"客户端能不能干活"
依赖于一次额外的往返：客户端在收到 `kAnswerId` 之前不知道自己叫什么，
服务端却已经把连接登记进表里了。主动告知把这两件事压缩到同一时刻，
少一个中间状态。`kAskId` 类型仍然保留，供客户端想主动确认时使用。

id 的来源按优先级：

| 顺序 | 来源 | 说明 |
|------|------|------|
| 1 | `allocatePeerId` 回调 | 上层按 peer 表分配，返回非空即采用 |
| 2 | `initialPeerId` 配置 | 兜底，静态指定的名字 |
| 3 | 空 | 安全默认值：转发一律被拒 |

**allocator 优先于静态配置。** 配了回调就意味着"上层知道谁该叫什么"，
它看到的是整张表；`initialPeerId` 只是一个字符串。两者都配时若让静态值
赢，动态分配就永远不会发生，而"配了不生效"是比"按文档规则生效"更难
排查的一类问题。

分配发生在**认证成功之后**，而不是连接建立时。理由：分配意味着"占了
表里的一个号"，握手失败的连接不该占号。放在更早的位置就需要为失败路径
补一次"还号"，而那条路径一旦漏掉就是号段泄漏。

`kAnswerId` 的 body：

```
u8  status      // 0 = 成功，非 0 = 分配失败（此时不带 id）
u8  idLen
u8  id[idLen]   // status == 0 时存在
```

长度用 `u8` 而不是通用约定的 `u16`，是为了与同一层级的路由字段（§9.1）
保持一致——同一个 id 不该有两套长度编码。

分配失败（allocator 返回空串且没有兜底）时，服务端仍然发
`kAnswerId(status != 0)`，**不断开连接**。理由：客户端此时只是不知道自己
叫什么，而"它能做什么"由服务端的身份绑定决定；断开会把一次可恢复的
容量问题变成一次不可恢复的连接失败。上层如果想拒绝，可以在
`onAuthenticated` 里主动关闭会话。

### 11.7 客户端声明标识（`kClaimId`）

服务端分配的 `client-N` 只适合"临时用一次"的场景。真实用法里，
用户需要**固定身份**：对照表存着"这一行永远发给 A"，A 的 id 一旦漂移，
下一批文件就会发给别人（真实发生过的事故）。所以协议允许客户端声明
自己的名字：

| 项 | 规则 |
|----|------|
| 谁定名字 | 客户端（`kClaimId`），不填则用服务端分配的 `client-N` |
| 唯一性 | 同一 id 同时只能有一条连接 |
| 撞名 | **拒绝**，不顶掉先到者、不自动改名 |
| 生命周期 | 与连接绑定：断开即释放，重连可再取回 |

`kClaimId` 的 body：

```
u8  idLen
u8  id[idLen]
```

时序：**认证完成之后**。服务端在认证成功时已经分配并告知了一个临时号，
声明成功即改名（§11.6 的 `kAnswerId` 再发一次，带上新名字）。客户端
收到 `kAnswerId(status == 0)` 且 id 与自己声明的一致时，才知道声明生效
——临时号那条应答可能晚于声明到达，不能拿它当结果。

应答复用 `kAnswerId`，status 取值：

| status | 含义 | 服务端动作 |
|-------:|------|-----------|
| 0 | 接受（回显最终 id） | 改表、把新身份通知对端 |
| 1 | 未分配（§11.6 的既有语义） | — |
| 2 | 该标识已被占用 | 只回 status，**不主动断开** |
| 3 | 标识不合法（空 / 超过 255 字节 / 含 NUL / 撞服务端 id） | 同上 |

**为什么拒绝时不主动断开**：`Connection::close` 会清空写队列，先发后关
等于把拒绝理由吃掉，客户端只能看到"连接断了"，分不清是撞名还是网络问题。
本项目客户端收到 2/3 会自己关闭；不听话的客户端也只是停在临时号上，
不构成权限问题。

**为什么撞名不自动改名**：id 是用户用来判断"发给谁"的键。自动改一个
后缀看起来"更友好"，实际效果是用户的对照表在不知情的情况下指向了另一个
人——这比连不上危险得多。同理，也**不允许**后来者顶掉先到者：那等于
允许任何人用别人的名字把对方踢下线。

**服务端 id 不能被占用**：`kClaimId` 的 id 等于服务端自己的 id 时按
`status = 3` 拒绝。原因在 §11.3 的路由顺序：`to == 服务端 id` 优先于
`to == 发送者自己`，一个叫 `relayerd` 的客户端永远收不到转发帧，症状是
"对方在线但发不过去"。

**身份变更的影响面**：改名后服务端要同步 peer 表与路由表，且此后
`from` 的绑定值、自投判定（§11.3）都用新 id。这些都由 `Session::assignPeerId`
一处完成，调用方只负责表册迁移。

### 11.8 远端目录列举（`kAskFileList` / `kAnswerFileList`）

用途：让发送方看到"对方接收目录里到底有什么"，这是**对照表粗校验**（"这行
要发的文件，对方是不是已经有了、大小对不对"）和远端浏览面板的前置。

**由对端客户端回答，中继只转发。** 服务端不做文件业务（`DESIGN.md` §3.1），
一旦让它列目录，"服务端不碰用户数据"这条边界就破了。

`to` 填对端 id（正常转发），`from` 由服务端按认证身份绑定——回信地址因此
是可信的，不能用帧里的自称。

**请求** `kAskFileList`：

```
u8  pathLen
u8  path[pathLen]   // 相对共享根；空 = 根目录本身
```

**应答** `kAnswerFileList`：

```
u8  status
u32 count
count × {
    u8  nameLen
    u8  name[nameLen]   // 仅文件名
    u8  type            // 0 = 文件，1 = 目录
    u64 size
    i64 mtime           // Unix epoch 秒
}
```

| status | 含义 | 带条目 |
|-------:|------|--------|
| 0 | 成功 | 是（`count` 条） |
| 1 | 路径不存在 / 不是目录 | 否 |
| 2 | 拒绝：未开启共享 / 绝对路径 / 越出共享根 | 否 |
| 3 | 条目过多，已截断到 5000 条 | 是 |

**为什么拒绝时也发 `count = 0` 而不是省掉字段**：解码侧不必为"有没有
count"分两种结构，少一条出错路径。

**上限 5000 条**：按每条约 20~60 字节算，帧体在 300KB 内，远小于帧上限；
而真实目录超过 5000 项时本来就该用筛选。截断用 status=3 明确告知，不假装
目录就这么多。

**条目名必须是单段**，即：非空、不等于 `.` 或 `..`、不含 `/`。这是线格式
的硬约束，不是建议——合法文件系统不可能给出这种名字，收到即说明对端有
bug 或被动过。

违背时**整份应答判为结构错误**，而不是跳过那一条。理由：坏条目只丢一条会
表现成"目录里莫名少了个文件"，比明确报错更难查；而出现一次不可信的名字，
说明这份列表的其余部分同样不可信。

反斜杠**不**在此列：Unix 允许文件名含它，那是合法文件。它是 Windows 的
分隔符，那层判断属于 UI 的平台语义（`ExplorerControl` 双击进入时处理）。
放在这里拦会把 Unix 上的合法文件当成攻击。

#### 11.8.1 安全模型

| 规则 | 说明 |
|------|------|
| 只暴露一个根 | `shareRoot` 配置项。空 = **不响应**（回 status=2），默认关闭 |
| 相对路径 | 请求里的路径一律相对 `shareRoot` 解释，绝对路径判为拒绝 |
| 越界检查 | 走 `PathPolicy::resolveWithin`，`..` 逃逸、盘符切换一律拒绝 |
| 只列一层 | 不递归。要看子目录就再发一次请求带路径 |
| 文件名不含路径 | 只回 `name`，调用方自己拼 —— 回的若是完整路径，接收端 UI 会以为能直接打开 |
| 名字必须单段 | 非空、非 `.`/`..`、不含 `/`；违背则整份应答判错（见上） |

**默认关闭是有意的**：能被别人看目录必须是显式决定，不能靠"忘了配置"
来默认开启。开启方式：CLI 的 `recv --share <dir>`；GUI 在「设定」→「共享」
里选目录（保存后断开重连生效——会话启动时已拷走配置）。

**只读一层 + 名字不含路径**这两条约束合起来，让"列举"不可能变成"遍历"：
对端能知道的只有共享根下第 N 层的直接子项，拿不到整棵树的清单。

### 11.9 远端取回（`kAskFilePull` / `kAnswerFilePull`）

§11.8 让发送方**看见**对端共享目录里有什么，本节让他在看见之后**拿走**。
没有它，"远端浏览"是个说不通的半成品：能看到文件却只能回头让对方发给你。

**只负责"请对方发"，不另造传输。** 取回的分块、Merkle 校验、续传、限速
全部沿用 §9 的会话机制，本节只解决"谁来发起"这一件事。

#### 11.9.1 时序

```
A                         S                         B
|-- kAskFilePull(path) -->|-- 转发 --------------->|
|<-- 转发 ----------------|<-- kAnswerFilePull ----|
|<-- 转发 ----------------|<-- kFileRequestSend ---|   B 主动发起一次正常发送
|--- kFileAnswerSend ---->|--- 转发 --------------->|
|<======= 数据块 / 完成 / 取消（§9.3 - §9.7）=====>|
```

B 回完 `kAnswerFilePull(status=0)` 之后，**立刻用普通的"推"流程**把文件发给
A：`kFileRequestSend` → `kFileAnswerSend` → 分块。A 侧不需要任何新逻辑——
它的常驻接收会话本来就在等文件，`kFileRequestSend` 到达即照常接受。

#### 11.9.2 为什么不用已经定义的 `kFileRequestDown`(502)

帧表里 502/503 是**占位**，名字看起来正合此题，但**在当前的传输模型
下是冗余的**：

- 拉模式下 A 不知道 `totalSize` / `chunkSize` / Merkle 根（它是接收方），
  这些参数只能由 B 在 `kFileRequestSend` 里给出——所以**无论如何都省不掉那
  一次 500**。
- `kFileAnswerDown` 的 body 与 `kFileAnswerSend` 同构（含 `resumeOffset`），
  若两条应答都发，A 会收到两个续传偏移，谁算数还得再定一条规则。

结论：502/503 只带一个路径，信息量比 500 少，加了它们等于**多一次往返换不到
任何东西**。它们保持未使用状态，代码里标注为保留占位。

#### 11.9.3 帧体

**请求** `kAskFilePull`（body 与 `kAskFileList` 同构，见 §11.8）：

```
u8  pathLen
u8  path[pathLen]   // 相对共享根；不允许绝对路径
```

**应答** `kAnswerFilePull`：

```
u8  status
```

| 值 | 含义 | 随后是否有传输 |
|---:|------|----------------|
| 0 | 已接受，马上用 `kFileRequestSend` 发给请求方 | 是 |
| 1 | 不存在，或是一个目录 | 否 |
| 2 | 拒绝：未开启共享 / 路径越界 / 当前正忙 | 否 |

**应答必须在发起传输之前发**：A 靠它区分"对方不给我"和"文件在传但很慢"。
把 status 塞进 `kFileRequestSend` 的 desc 里做不到这一点，因为 A 在收到 500
之前根本不知道有没有回应。

#### 11.9.4 共享即"可见且可取"

`shareRoot` 一个开关同时管列举和取回，**不再单独设"只读/可下载"**。

理由：只想让人看、不想让人拿，这个场景在点对点工具里不成立——对方截个图
或自己发一次就能绕过。多一个开关只会多一处用户会设错的地方，还会让"我明明
共享了却拿不走"变成一个需要排查的问题。

#### 11.9.5 边界

| 不做 | 理由 |
|------|------|
| 批量/目录取回 | 目录要先打包（§11.6 的归档帧还没实现），否则就是 N 次独立取回，语义含糊 |
| 断点续传的跨会话恢复 | 沿用 §9 的会话内续传；A 侧落到接收目录后与普通接收无差别 |
| 指定远端保存位置 | 落点是**请求方**的接收目录（由它自己配置），共享方无权指定 |

### 11.10 目录取回（`kAskArchivePull`）

§11.9 只取单个文件。取目录时若让请求方逐个文件要，会退化成 N 次往返，
而且"目录里有哪些文件"与"取的时候又变了"之间有竞态。这里让对端**先打包
再一次发过来**，一次往返解决。

#### 11.10.1 为什么单独一个帧，而不是让 `kAskFilePull` 猜

`kAskFilePull` 的路径可能指向文件也可能指向目录。让对端"看着办"看着省事，
但两件事的失败模式与代价完全不同：发文件是"打开就发"，发目录要先遍历、
压缩、写临时文件，可能是几秒到几十秒的活。请求方必须能明确表达自己要哪种，
否则"对方正在压缩，别催"这种状态没法呈现。

应答复用 `kAnswerFilePull`：结论就是同一类（接受 / 不存在 / 拒绝），
状态码含义完全一致，没必要为"接受的是一次打包"再定义一套。

#### 11.10.2 时序

```
A                              S                              B
|-- kAskArchivePull(dir) ----->|-- 转发 ---------------------->|
|                              |      （B 遍历 + 压缩，可能要几秒）|
|<-- 转发 ---------------------|<-- kAnswerFilePull(0) -------|
|<-- 转发 ---------------------|<-- kFileRequestSend(包) -----|
|-- kFileAnswerSend ---------->|-- 转发 ---------------------->|
|<========== 数据块 / 完成 / 取消（§9.3 - §9.7）==============>|
```

**应答在打包完成之后才发**，不是收到请求就回 0。理由：打包可能失败
（磁盘满、权限、文件在压缩过程中被删）。先回 0 再失败，请求方只能看到
"对方答应了但没来东西"，直到会话空闲超时才报错——那是所有失败里最难查的一种。

代价是请求方必须等得住。归档请求的应答超时是 **120 秒**（文件取回是 10 秒），
这个差别是刻意的：同一个 10 秒对"打开文件"够用，对"压缩一个目录"不够。

#### 11.10.3 打包参数（写死，不协商）

| 项 | 值 | 理由 |
|---|---|---|
| 格式 | tar.xz | 单文件流式，损坏时前面条目还能救；LZMA2 对源码/日志压缩率好 |
| 压缩级别 | 1 | 传输场景下网络是瓶颈，压缩比的边际收益远小于"用户多等 30 秒" |
| 文件数上限 | 20000 | 超过则拒绝（status=2），提示分批 |
| 总字节上限 | 256 MiB | 同上。压缩是**同步**做的，见 11.10.4 |
| 归档内路径 | 相对请求的那个目录 | 包里第一层就是 `dir/` 的内容，解出来不会多一层同名目录 |
| 包名 | `<目录名>.tar.xz` | 请求方靠它知道落到本地的是什么 |

#### 11.10.4 压缩是同步做的（已知代价）

`kAskArchivePull` 在**发起方的事件循环里同步打包**，期间该连接不处理其他
帧（包括心跳）。这是有意接受的取舍：

- 放到后台线程要处理"线程还在跑、Client 已析构"的生命周期问题，以及
  "打包完成后如何安全地回到事件循环"；
- 上限 256 MiB + 级别 1 把最坏耗时压在十秒出头，在心跳超时（30 秒）以内。

**这是一条会在真实链路上被检验的假设**：慢盘（网络盘、机械盘）上打包耗时
可能远超估算。真遇到再上后台线程 + 进度帧（`kAnswerArchiveReady` 那组
占位帧就是为异步准备的，目前保持未使用）。

#### 11.10.5 临时文件与清理

包写在**系统临时目录**，不在共享根里——放共享根会让对端在列举时看到它，
也会污染用户自己的目录。

传输结束（成功、失败、取消都算）后删除。进程崩溃时残留的临时文件由系统
清理，不额外做启动扫描：为了清理几个可能不存在的文件而在每次启动时扫目录，
代价大于收益。

#### 11.10.6 请求方收到的是什么

**一个目录。** 包在落地后被自动解开、删除，用户看到的层次与对方一致
（`<接收目录>/<目录名>/…`）。

解包位置是 `<包所在目录>/<包名去 .tar.xz>/`，不是包的父目录：包内路径是
"相对被请求的那个目录"的（§11.10.3），没有顶层目录。解到父目录会让
`a.txt`、`nested/` 散在接收目录里，与对方看到的层次不符。

**解包失败时保留包**并报错。用户还能自己解，总比"包被删了又没解开"好。

自动解包是**逐次**决定，不是全局开关：`kAskArchivePull` 的请求方知道自己
要的是目录，但**别人主动发来的 `.tar.xz` 不会被擅自解开**——那可能正是
用户想收的包。CLI 的 `--unpack` 是显式要求全局解包时的开关。

初版（2026-10-23 上午）只把包发过来、不解释放。当天补成自动解包：拿到一个
包却不解释放，"下载目录"对用户仍然只算半成品。
